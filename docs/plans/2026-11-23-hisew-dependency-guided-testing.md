# WebVOWL dependency-guided testing for HISEW

**23 November 2026 · Draft implementation plan · Proposed HISEW route R2**

## Proposed outcome

Extend WebVOWL’s existing `graph:dependencies` and `check:affected` commands. Give both commands the same graph of imports, file inputs, generated outputs and their consumers. During a HISEW execution, use the graph to explain which tests can distinguish a changed behavior and to find additional obligations that import analysis misses. HISEW remains the authority for dispatch, candidate custody and receipts. A repository list or test report has the scope of the observation it records.

The agreed first delivery includes the graph, a HISEW handoff and one real WebVOWL data or fixture edit that runs a smaller local Jest set. A graph-guided handoff through the admitted full HISEW suite satisfies the HISEW delivery criterion. Automatic narrowing inside the HISEW engine is a separate change justified by measured savings. Keep build, browser, corpus, Node probe, Python and hosted CI obligations applicable through their owning commands. Automate stable tool version discovery and npm lockfile regeneration in execution preparation, with approval of the exact configuration effects before regeneration. The owner selected planning only for dependency refresh.

## 2. Requirements and acceptance criteria

- **REQ-001 · AC-001 — One refreshable dependency graph.** An ordinary export includes disconnected authored modules and tests, native imports, supported resource and artifact relationships and diagnostics. Focus and selection agree on the snapshot, edge and witness for each shared example. Reordering observations does not change a semantic digest. A native unresolved Node import still fails. Raw notes distinguish native resolution failures from imports proved to belong to the browser context.
- **REQ-002 · AC-002 — Cumulative change selection.** Use the accepted immutable comparison and current testable bytes. Include committed, staged, unstaged and new authored files, both rename endpoints, removals and changed tests. Traverse base and candidate independently and union the selected current Jest paths. Each proposed test has a direct-change or dependency-path witness. Additional literal paths widen the relevant envelope. Uncertain input disposition produces explained full coverage or a refusal.
- **REQ-003 · AC-003 — File and generated-output coverage.** Supported file reads, workers and a producer/output/consumer chain appear automatically with source evidence, including when a tracked input is renamed. A change with no import edge still reaches its known test or owning verification command. An unresolved loader cannot quietly drop a possible consumer. Build and workflow outputs carry producer context and distinguish declared relationships from bytes observed in a specific run.
- **REQ-004 · AC-004 — HISEW use with attributable proof.** An operator carries a changed behavior and its graph witnesses into an authorized HISEW execution. HISEW independently admits the scope and records the candidate, commands or tests, and actual verdicts. Demonstrate the handoff using the admitted full suite if HISEW cannot admit the proposed subset. Discovery, missing verdicts, skips and separate local reports retain their actual evidentiary scope.
- **REQ-005 · AC-005 — Safe, useful targeting.** On one real WebVOWL data or test-fixture edit, the maintained local selector must execute fewer Jest files than the independent full inventory, exercise the named affected assertion and agree with the full run for the selected files. Complete the existing build, browser and corpus checks applicable to that edit. A deliberately omitted failing test makes the independent full shadow run fail. Unsafe inputs, path escapes, source drift and unsettled processes yield no successful selection or execution evidence. Compare planning plus execution with the independent full run before recommending the narrow route for routine use.
- **REQ-006 · AC-006 — Automated, reproducible version refresh.** Preparation detects newer stable versions and lock/install drift. After exact approval, npm regenerates the approved lock delta against the selected stable releases and CI reference runtime. Review the actual graph and verify using a frozen install. Unapproved dependency changes or observed version drift trigger review before verification proceeds.

### DEC-002 · Refresh versions automatically before freezing a candidate

The observed lock and installation matched for dependency-cruiser `18.8.0`, ESLint `10.15.0`, Jest `30.5.2`, Vite `8.3.8`, `vite-plugin-static-copy` `4.1.1` and `yaml` `2.9.1`. Official npm metadata on 23 November returned the same stable versions except dependency-cruiser `18.9.0`, published on 22 November. WebVOWL already pins Node `26.13.1`, the latest applicable Node LTS patch observed at planning. The registry and public release are version evidence. The probes above used `18.8.0`. [dependency-cruiser release](https://github.com/sverweij/dependency-cruiser/releases/tag/v18.9.0) · [Node LTS release](https://nodejs.org/en/blog/release/v26.13.1)

1. At preparation, read the root lock and installed versions. Query the official stable `latest` tags for the selected graph toolchain and check Node’s LTS channel. Retain exact versions, engines, dependency changes, registry integrity and notices. Report unavailable registry data or local lock/install mismatch explicitly. Use the project’s existing runtime selection and npm as the peer and lock authority. Scope the refresh to graph tooling and required transitives.
2. Produce a scoped update proposal from that data. For the observed delta, the smallest edit is the root `package-lock.json` entries for `node_modules/dependency-cruiser` (`18.8.0` → `18.9.0`, including its new exact `ignore` constraint) and `node_modules/ignore` (`7.0.14` → `7.0.16`), with npm-generated integrity and resolution fields. Stylelint also consumes the shared `ignore` 7.x copy, so include lint in the compatibility witness. The root `>=18.8.0` range already admits `18.9.0`. If implementation requires a higher supported API floor, identify the exact `package.json` setting and obtain approval for that edit too. [Prior dependency management decision](development-dependency-upgrade.md) · [npm update](https://docs.npmjs.com/cli/commands/npm-update)
3. After the exact edit is approved, use the repository-selected npm in the approved preparation workspace with lifecycle scripts disabled. Qualify the scoped `npm update dependency-cruiser --package-lock-only --ignore-scripts --no-audit --no-fund` invocation against the approved versions and inspect the native diff. An unrelated change or resolution different from the proposal stops incorporation. Use the resulting exact lock for script-disabled installation and selected checks. Take a new approval for a changed candidate. Preserve the repository’s frozen install semantics, including `npm ci` in CI. [WebVOWL setup and CI](../continuous-integration.md) · [npm ci](https://docs.npmjs.com/cli/commands/npm-ci)
4. Freeze the resolved versions before graph generation and testing. A subsequent release becomes input to the next preparation or to a deliberately reconsidered candidate. Keep this an execution-preparation operation with a proposal and exact write approval. A new bot, schedule, CI job or moving registry lookup during verification would introduce a separate authority and is outside this change.

The cumulative implementation candidate includes the approved lock or tooling edits and should exercise the existing full fallback for those changes. Use independently owned fixtures for adverse controls. For the required real resource pilot, compare the actual WebVOWL file edit against a separate accepted baseline with matching graph, runner and lock controls. Keep the implementation execution’s original comparison through handoff.

### DEC-003 · One snapshot graph for export, focus and selection

- Compose native imports, automatically observed relations and existing reviewed exceptions into an immutable view per snapshot. Use literal repository-relative `/` paths for authored nodes, scoped artifact IDs for generated outputs, and distinct external endpoints. Label dependency edges with their kind, source path and location, resolver context and whether they come from a native observation or a reviewed declaration. Use dependent → dependency consistently. For example, a reader depends on a generated artifact and the artifact depends on its writer. Walking backwards from a writer reaches the artifact and then its consumers.
- Add versioned `dependencies.json` to the existing bundle. Keep `graph.json` as the original native diagnostic member and `declared-relations.json` as the original policy witness. Bind all members to the existing atomic publication and digest readback. Derive new typed views from `dependencies.json`. Keep existing Node-context Mermaid views labelled with their native input digest. The bundle can retain valid diagnostics when policy findings prevent selection. Design the proposed optional `--focus <literal-path-or-artifact-id>` on `graph:dependencies` to return direct and transitive consumers with witness paths. Full capture precedes focus. An unknown focus gets an explicit diagnostic.
- Build a reverse index once per snapshot and use the same cycle-safe traversal in focus and `planAffected`. For selection, retain one deterministic shortest witness to each selected file, or a direct-change reason. Keep the full graph for alternate paths when reviewers need them. Use separate old and new traversals so a witness never crosses between different source states. Expand reviewed directory relations from the admitted inventory once or index their prefixes. The review should verify linear traversal in visited nodes and edges, plus the emitted witness data, and absence of a new cruise or full policy scan per seed or relation round.
- Preserve the existing `check:affected` flags and meaning of list, selected, full and shadow. Bind decisions to base tree, candidate HEAD/tree, index and file digests, the independent Jest inventory, policy and tool identities. Add typed reasons and diagnostics with a versioned report change if the data contract changes. Keep `--path` in the repository CLI as an additive change seed. HISEW `--additional-path` takes a test file from its own inventory. A test path discovered by one tool needs independent admission at the HISEW interface.
- Keep historical analysis data-only. Use Git objects for exact source and relevant JSON/YAML metadata under the existing bounds. Other files can be identity or resolution leaves when their bytes have no role in discovery. Do not mistake a placeholder for captured bytes. Account for staged input that differs from both observed base and runnable bytes. If the planner cannot bound the effect of that unobserved relationship, take the full path. Keep deleted tests, incompatible controls, unknown seeds, ambiguous paths, unknown relevant loaders and empty reachability conservative.

## 4. Use during a HISEW execution

1. **Start from the accepted comparison.** Reinspect the loaded HISEW setup and exact worktree `status`. For a later explicitly authorized R2 execution, start through the native launcher with accepted UTF-8 requirements and digest or admitted snapshot ID, route record, software-selection reference and owner channel. The installed start operation owns binding an unregistered worktree. Retain execution ID, generation, owner term and the accepted comparison. Resolve native Work/Evidence before allocating graph or shadow artifacts. Keep owner secrets in the documented private stdin channel.
2. **Propose and review coverage.** Run `npm run graph:dependencies -- --output <new absolute Work destination>` and `npm run check:affected -- --base <accepted full commit> --list`. After the focus slice, use `--focus` on the graph command for a single literal resource or artifact. Read the changed functions, guards and inputs, the graph witness and the actual test assertions. Retain the seed and independent oracle, tests and required environments, the reason for any omission, unresolved relationships and further checks. Repeat the selection for relevant candidate or dependency changes. Keep the same cumulative comparison across implementation checkpoints.
3. **Ask the engine to admit the verified scope.** In an active execution, use `hisew verify-change-execution --session-host codex --selection affected --list-only`. Repeat `--additional-path <test-file>` for independently required, discovered files. Use `--verification-head` only for an exact committed candidate when the checked bytes match. Compare the engine’s scope with the repository report. Admit accepted adverse or positive conditions through `record-behaviour-acceptance` when the undertaking uses it, with independent review of each named oracle. Use the supported native dispatch and receipt inspection for the admitted scope. [HISEW verification obligations](https://github.com/Hadden-Industries/software-engineering-workflow/blob/fb968e27946e5bc78c8702c123e4c42029c3f17b/method/verification-obligations.md)
4. **Use a conservative native route when the subset is unavailable.** The inspected SQLite reservation calls its own selector and can refuse affected JavaScript selections for incomplete native discovery before considering `--allow-fallback`. Its exact-command, custom report and requirements options in generic help are rejected by this SQLite path. The standalone native Jest provider uses `--findRelatedTests` and the special Markdown/JSON Quality adapters do not consume WebVOWL’s graph. Preview `--selection all --list-only` when the native subset is unavailable. Dispatch the admitted broader scope, using `--allow-fallback` where the engine reports that a wider obligation needs acceptance. Use maintained full Jest and independent checks for any remaining applicable proof. Report any unmet native receipt as outstanding. A local selected or shadow run is scoped operator evidence. [Deferred typed-input adoption](https://github.com/Hadden-Industries/software-engineering-workflow/issues/150)
5. **Route native narrowing as a separate change.** Revisit it after measured net savings and when a supported HISEW release exposes the necessary typed inputs and result admission. Have the HISEW owner approve the adoption and timebox. That undertaking needs an end-to-end pilot binding the execution base, working or committed identity, full inventory, reported fallback and exact terminal test verdicts. Include a required test missing from the adapter result, forged or stale identity and interrupted-run controls. Use the installed engine’s supported interfaces.
