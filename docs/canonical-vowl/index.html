Canonical VOWL is a versioned, producer-neutral JSON representation of a normalized VOWL visual ontology model. Conforming producers of the same normalized model emit identical bytes, so a document can be digested and signed. This specification defines the structural-content, artifact and compatible-artifact profiles, their closed data model, the internal RDF mapping and RDFC-1.0 labelling that assign document-local identifiers, the RFC 8785 encoding and its exact decoding, the mapping from OWL 2 ontologies, and the one-way migration from the historical VOWL-JSON that WebVOWL exported, a format previously defined only by its implementations.
Canonical VOWL is an experimental candidate. Corrections that are justified by an error or an accepted requirement may still change schemas, mapping rules, identifiers and canonical bytes; each candidate is identified by its revision. The `/v1` suffix in the profile identifiers names candidate profiles, not a stable interoperability promise. A copy of this draft is identified by the Git commit of the repository that contains it, and anything that claims to follow it should cite that commit. This draft consolidates every section from the source documents listed in [[[#changes]]], which records for each document which parts are consolidated, superseded or out of scope. This document specifies the interchange format. The JavaScript package interface, the atomic editing operation, the live-model and session operations, and the display-order keys are application programming interfaces of the reference implementation; they are documented in the [`vowl` package README](../../packages/vowl/README.md) and their amendment records, not here. Adoption of Canonical VOWL by OWL2VOWL or any other body would be a separate governance decision.
## Introduction Canonical VOWL is a versioned, producer-neutral JSON representation of a normalized VOWL visual ontology model. Its retained structural information and, for the artifact profiles, portable visualization state are mapped to one closed data model and encoded as RFC 8785 [[RFC8785]] bytes, so conforming producers of the same normalized model emit identical bytes. Canonical VOWL identifies a VOWL representation. It does not identify the source document bytes, the complete OWL axiom inventory, or every OWL ontology with the same entailments. ### Background {#background} The VOWL 2 specification [[VOWL2]] defines a visual notation for OWL ontologies: its graphical primitives, colours and splitting rules. It defines no data format. The VOWL article [[VOWL-ARTICLE]] names VOWL-JSON as the format WebVOWL uses without specifying it. In practice that format was defined by its implementations, first OWL2VOWL and later this repository's reconstruction of OWL2VOWL in JavaScript, and the reconstruction had to be derived from their behaviour. Deterministic-looking JSON is still not a canonical semantic format. RFC 8785 deliberately preserves array order; it cannot remove arbitrary producer identifiers, normalize a graph, distinguish sets from sequences, or decide which OWL information belongs in VOWL. RDF Dataset Canonicalization [[RDF-CANON]] labels anonymous RDF structure, but VOWL JSON is not RDF and first needs an injective mapping. Canonical VOWL is therefore a formally specified successor to VOWL-JSON, not a description of it. It keeps what VOWL-JSON was for and replaces its parallel-array shape, which loses distinctions that a visualization needs. That is an intentional format break: existing files enter Canonical VOWL only through the one-way migration in [[[#migration]]]. No inspected VOWL specification defines a canonical byte representation, and neither RFC 8785 nor RDFC-1.0 defines VOWL's semantic normalization, so this specification formulates one while reusing those standards for the jobs they specify. ### How Canonical VOWL works {#overview} Canonicalization composes three operations: 1. normalize a producer-neutral VOWL source model; 1. assign deterministic document-local identities to anonymous graph objects, by mapping the model to an internal RDF dataset and labelling it with RDFC-1.0; and 1. encode the resulting closed JSON document as RFC 8785 UTF-8 bytes. The structural-content and artifact profiles are projections of the same source model, not separate formats maintained by separate builders. ### Goals {#goals} Canonical VOWL aims to: 1. produce byte-identical output for the same normalized VOWL model across conforming producers, locales, runtimes, and supported source syntaxes; 1. provide exact bytes suitable for external digests and detached signatures; 1. retain the VOWL-relevant distinctions that the historical parallel-array representation loses; 1. separate ontology identity, semantic roles, VOWL constructs, and visual occurrences; 1. support anonymous and symmetric structures without retaining producer identifiers; 1. preserve full annotation predicates, values, lexical forms, and nesting; 1. distinguish unordered sets from ordered, repetition-permitting sequences; 1. preserve one source of truth for every canonical fact; 1. keep strict and compatibility OWL mapping behind one canonical core; 1. provide an explicit one-way migration route for named historical dialects; 1. reject ambiguous, unsupported, or noncanonical input instead of guessing; 1. protect graph canonicalization from pathological resource consumption; and 1. remain usable as the input to a VOWL visualization, rather than becoming a second general-purpose OWL serialization. ### Non-goals {#non-goals} Canonical VOWL does not: - define OWL semantic or entailment canonicalization; - preserve every OWL axiom or ABox assertion; - preserve source syntax, prefixes, whitespace, comments, document URLs, redirects, cache locations, or retrieval history; - claim that VOWL JSON is JSON-LD or an RDF concrete syntax; - embed a digest, signature, key, proof, producer, mapper, migration record, diagnostic, or acquisition provenance; - retain historical OWL2VOWL output as an alternative output mode; - detect historical dialects automatically; - provide durable identifiers for anonymous expressions or visual occurrences; - reproduce a layout engine's future trajectory; - reproduce CSS, themes, fonts, DOM state, viewport pixels, device-pixel ratio, hover, selection, search, or open sidebars; - register a new media type; or - implement cryptographic signing or digest algorithms. ### Boundary examples {#boundary-examples} - Turtle and RDF/XML sources that resolve to the same retained closure and normalized VOWL model produce identical structural-content bytes. - Two OWL ontologies with the same entailments but different retained asserted VOWL structures need not produce identical bytes. - Pretty-printed JSON with sorted object keys and sorted arrays is repeatable output, but it is not Canonical VOWL unless it also satisfies the closed model, graph labelling, set and sequence, validation, and exact RFC 8785 rules of this specification.
## Conformance This specification defines six conformance classes: - A Canonical VOWL document is a byte sequence that is the [=canonical encoding=] of a document of one of the profiles in [[[#identifiers]]]. - A canonicalizing producer takes a [=normalized source model=] and a profile, and either emits the [=Canonical VOWL document=] for them or fails with a defined error. - An exact decoder accepts exactly the [=Canonical VOWL documents=] of the profiles it supports and rejects every other input without repairing it. - An OWL mapping adapter maps the imports closure of an OWL 2 ontology to a structural-content document under one of the OWL mapping profiles in [[[#mapping-profiles]]]. - A migration adapter converts input in a named historical [=dialect=] into a [=Canonical VOWL document=] as specified in [[[#migration]]]. - A renderer draws a [=Canonical VOWL document=] as a VOWL visualization, as specified in [[[#projection]]]. The requirements for each class are stated in the sections that define its behaviour.
New in consolidation: the source documents state these requirements but never named the classes; naming them here changes no requirement. The renderer class gathers the obligations that the sources place on whatever draws the model. What a conformance claim names is specified in [[[#conformance-claims]]].
## Terminology and notation {#terminology} ### Definitions {#definitions}
profile
A versioned identifier that, together with a revision of this specification, fixes a closed grammar and every rule that can affect conforming bytes.
structural-content profile
The profile that binds normalized VOWL structure and visual topology.
artifact profile
The profile that binds the same semantic content as the [=structural-content profile=] plus portable, static visualization state.
compatible-artifact profile
The experimental profile that captures retained structure, a complete scene and portable interpretation qualifications together.
normalized source model
The producer-neutral model that a [=canonicalizing producer=] validates, labels and encodes.
occurrence
An addressable visual projection of retained semantic records, with a deterministic semantic context and no independent copy of their meaning.
canonical ID
An identifier issued within one admitted document after canonical labelling. It is local to that document, and a structural or visualization change can relabel it.
dialect
A historical input format that a [=migration adapter=] recognizes only by its exact identifier.
diagnostic
An immutable record of an adapter decision or a discarded input field. Diagnostics are never part of canonical bytes.
### Notation {#notation} Every field listed in a record is required unless suffixed `?`. No other fields are allowed. `Set` means a duplicate-free array of zero or more values of type `T`; `Set1` requires at least one. `Sequence2` is an array of at least two values; it preserves order and permits repetition. Only property-chain `members` is a sequence in version 1; every other array in this specification is a set. Canonical set ordering is the complete-member RFC 8785 UTF-8 order of [[[#collections]]], applied inside out after IDs are assigned. Source set order is immaterial. `Text` is a [=Unicode-valid=] JSON string ([[[#unicode-admission]]]). `Token` is an exact, case-sensitive ASCII discriminator or diagnostic code from the tables of this specification. `IRI` is a string satisfying the `IRI` production of RFC 3987 [[RFC3987]] with a scheme; fragments are allowed, as RDF IRIs require. It is not restricted to HTTP URLs and is not passed through WHATWG URL serialization. IRI identity is lexical: no case folding, percent-decoding, Unicode normalization, or network lookup. `Decimal` matches `0|[1-9][0-9]*` and represents a nonnegative integer without conversion to binary64. `Number` is a finite binary64 value other than negative zero. `Boolean` is a JSON boolean. References are strings, resolved in these exact categories: | Type | Target | | --- | --- | | `S` | Subject record. | | `R` | Role record. | | `X` | Expression record. | | `K` | Construct record. | | `O` | Occurrence record. | | `C` | A `class` or `rdf-class` role, or a class-sort expression. | | `D` | A `datatype` role or a data-sort expression. | | `P` | An `object-property` role or an `object-inverse` expression. | | `DP` | A `data-property` role. | | `RP` | An `rdf-property` role. | | `AP` | An `annotation-property` role. | | `I` | An `individual` role, including one over an anonymous subject. | Canonical reference spellings use the category prefixes and issuance rule of [[[#id-issuance]]]. Source references instead use arbitrary nonempty `Text` handles, unique across all five record categories. The same field name `id` carries a source handle before canonicalization and a [=canonical ID=] afterwards. `id` is never itself encoded as a fact in the internal RDF dataset. An annotation's IRI value is an `IRI`, not a reference, even when its spelling equals a handle. ## Authority and interpretation {#authority} The normative dependency order is: 1. this specification, with its executable schemas implementing its closed grammar, for VOWL-specific meaning; 1. the VOWL 2 specification [[VOWL2]] for visual mapping, where this specification has not deliberately tightened or extended it; 1. the OWL 2 Structural Specification [[OWL2-SYNTAX]] for OWL structures, sets, sequences, annotations, imports, and anonymous individuals; 1. RDFC-1.0 [[RDF-CANON]] for the canonical labelling of this specification's internal RDF dataset; 1. RFC 8785 [[RFC8785]] for the final JSON serialization; and 1. RFC 7493 [[RFC7493]] for the I-JSON input restrictions that RFC 8785 relies on. Where historical OWL2VOWL JSON, the reference builder, or a Java OWL2VOWL result conflicts with this specification, the historical shape is migration input ([[[#migration]]]), not normative Canonical VOWL. VOWL 2 defines a visual notation, concentrates primarily on the TBox, and does not define a glyph for every OWL 2 structure. Retaining an OWL structure and drawing it with standard VOWL notation are separate claims. Version 1 introduces no extension glyphs, and a historical WebVOWL glyph is not sufficient authority to call an extension standard VOWL 2.
The canonical locations of the VOWL 2 specification no longer resolve. This specification relies on a third-party recovery, [pinned in this repository](../owlapi-js/conformance/upstream/vowl-2/index.html) by Git revision and per-file SHA-256. Its content identity is well corroborated, but its byte identity with the 2014 original is not established ([ADR 0004](../adr/0004-vowl-specification-as-correctness-authority.md)).

### Source model {#source-model} The [=normalized source model=] is plain, acyclic structured data. Producers use local string handles only to express references among source records. Handles MUST be unique within the input, and their spelling and encounter order MUST NOT affect canonical identity; handles never appear in output. Object identity in the producer's programming language is not a reference mechanism: every reference is an explicit handle.
Explicit handles keep the model language-neutral and testable by independent producers.
### Record categories {#record-categories} The structural model has five nonoverlapping categories: 1. **subjects**: annotation-capable identity bearers, named by an absolute IRI or anonymous within the resolved closure; 1. **roles**: a subject's semantic role, as a class, RDFS-only class, datatype, object property, data property, annotation property, individual, or genuinely generic RDF property; 1. **expressions**: typed class, object-property and data-range expressions; 1. **constructs**: normalized relationships, groups, assertions and other VOWL-relevant statements; and 1. **occurrences**: visual nodes, edges and movable labels that project roles, expressions or constructs ([[[#projection]]]).
These categories replace the historical parallel `class`/`classAttribute` and `property`/`propertyAttribute` arrays ([[[#migration]]]). That removes hidden joins, copied attributes, traversal IDs, and the need to mutate one half of a record while reconciling the other.
### Canonical IDs {#canonical-ids} Every referenceable record receives a category-specific, opaque [=canonical ID=] such as `s0`, `r0`, `x0`, `c0` or `o0`. Canonical IDs are: - issued from the RDFC-1.0 canonical identifier map ([[[#id-issuance]]]); - local to one document and profile; - recomputed after a material edit; - permitted to differ between the structural and artifact projections of the same source; and - never copied from an OWL blank-node label or a historical OWL2VOWL ID. A canonical ID MUST NOT be used as standalone external or durable identity; named semantic identity remains the subject's absolute IRI. An external reference to an occurrence MUST bind both the immutable document digest and the occurrence's canonical ID. Consumers MUST NOT join profiles, revisions or artifacts by comparing canonical ID strings. The structural semantic source is shared across profiles, but the serialized `structural` object is not byte-identical between profiles: artifact-only facts take part in whole-profile labelling, so that coordinates cannot be associated with the wrong member of an anonymous symmetry class. Encounter order is never an ID issuance rule; [[[#id-issuance]]] specifies the category partition and ordinal assignment. ### Document envelope {#envelope} The source envelope is `{structural, visualization?}`. The operation's profile selects the [=structural-content profile=] or the [=artifact profile=]; the core has no implicit profile default. A [=canonicalizing producer=] MUST reject `visualization` when the structural-content profile is selected, rather than silently dropping supplied state, and MUST require it when the artifact profile is selected. The canonical document adds the exact profile identifier as `profile`. `structural` is the closed record `{ontology: Ontology, subjects: Set, roles: Set, expressions: Set, constructs: Set, occurrences: Set}`.

### Assertion anchors {#assertion-anchors} Every source-axiom annotation is carried by an `assertion-anchor` construct, by one uniform rule, rather than being copied onto an aggregate in some cases and stored separately in others. `Assertion` is an embedded copy of any base construct shape above, with its `id` removed and excluding `assertion-anchor`, or the declaration `{kind: "declaration", role: R}`. - An anchor retains the pre-aggregation assertion after scalar and expression normalization, together with the exact set of source-axiom annotations on that assertion. - Annotations MUST remain attached to the exact assertion they annotate. - Anchors MUST NOT contain other anchors; nested annotations use `Annotation` recursively. - Different annotation sets produce different anchors, and repeated identical anchors MUST be deduplicated. - An anchor MUST be supported by the corresponding base fact, declaration role or endpoint aggregate, and MUST NOT introduce an unrelated assertion whose normalized meaning is absent. The target of an endpoint anchor MUST be the aggregate target itself or one immediate operand of the aggregate intersection. - Unannotated source assertions are not inventoried merely to preserve their spelling, and the model does not claim to reconstruct discarded unannotated axioms. For example, domains `A` and `B` normalize to one domain construct targeting `class-intersection(A, B)`. An annotation on the original domain `A` is carried by an anchor whose embedded assertion still targets `A`, so the annotation is not falsely attached to the combined intersection. The same rule applies to an annotated subclass, declaration, characteristic or annotation assertion, even when no aggregation occurred.
Anchors are not a complete source-axiom inventory. They are the minimum information needed to preserve retained first-class OWL annotations without duplicating unannotated source structure.
### Individuals {#individuals} Version 1 retains the individual information that VOWL's class-associated presentation of individuals needs; it is not a general individual graph format. The model retains: - individual roles created by retained declarations or use; - directly asserted class memberships, including memberships in complex class expressions; - individuals referenced by retained enumerations and value restrictions; and - annotations on retained individual subjects and on class-membership constructs. It excludes: - inferred class memberships; - individual counts derived from subclasses or by a reasoner; - positive and negative object-property assertions; - positive and negative data-property assertions; and - same-individual and different-individual axioms. Excluded constructs MUST NOT be approximated; the mapping reports them outside canonical bytes ([[[#owl-mapping]]]). A future profile may add an individual graph, but it MUST use a new profile identifier, and MUST NOT be a flag that changes version 1 bytes. Historical `instances`, `individuals` and per-class counts are not canonical truth. A renderer derives direct, unique membership counts from retained class memberships, without a `sameAs` quotient or inference. An IRI with both class and individual roles remains two roles, and an individual equality statement MUST NOT be promoted to class equivalence. ### Normalization {#normalization} Normalization is a finite structural procedure, not inference: 1. Resolve the selected closure, and standardize anonymous subjects apart by source ontology before erasing acquisition provenance. 1. Establish named subjects, typed roles, and the finite annotation and datatype signature closure ([[[#subjects-and-roles]]]). 1. Normalize literals, explicit default cardinality fillers and typed expressions, preserving lexical values and constructor nesting. 1. Build each unannotated base-construct payload and deduplicate exactly equal payloads; separately, build anchors for annotated source assertions. 1. For each exact pair of property and endpoint kind, deduplicate the endpoint targets. One target is used as it is; two or more become one immediate intersection, without flattening nested expressions. A generic RDF range containing both class and data targets is ambiguous, and MUST fail rather than select a category. 1. Generate and validate the complete occurrence projection ([[[#projection]]]). 1. For an artifact, attach complete explicit state to those occurrences before whole-profile labelling ([[[#artifact]]]). Normalization MUST NOT perform inverse-endpoint propagation, equivalent-property domain inference, reasoner closure, property-characteristic expansion, transitive closure, algebraic simplification, satisfiability checking, weakest-bound selection, or numeric lexical canonicalization. - Missing property domains and ranges are projection defaults ([[[#projection]]]), not asserted domain or range constructs. - Multiple domain or range axioms normalize to an intersection, so a directly asserted intersection and the equivalent collection of separate unannotated endpoint axioms produce the same model. - Grouping equivalent classes for rendering does not add inferred equivalence constructs. - Declarations add roles, annotated declarations add anchors, and redundant unannotated declarations add nothing.
- **Positive instance:** an unannotated pair of domain assertions for `A` and `B`, and a single domain assertion for the direct intersection of `A` and `B`, have the same normalized endpoint. - **Negative instance:** attaching an annotation to `A`'s assertion changes the retained anchor, and therefore the canonical model. - **Near miss:** replacing a repeated property chain `[p, q, p]` with `[p, q]` changes an ordered construct, and so changes the result.
### Uniqueness {#uniqueness} Primary-record uniqueness is semantic within each category, not equality of raw JSON that contains different `id` values: - subjects and roles use the keys of [[[#subjects-and-roles]]]; - expressions use the structural key of [[[#expressions]]]; - constructs use their complete typed payload except `id`; and - occurrences use the generation key of [[[#projection]]]. Anonymous subjects remain distinct, nominal subjects in these comparisons, even when a whole-graph automorphism can exchange them. Exact duplicates in a source set MUST be rejected after scalar normalization, so that differently cased language tags cannot evade uniqueness. ### Collections and ordering {#collections} Every array field is either a **set**, unordered and duplicate-free, or a **sequence**, ordered and permitting repetition where its construct allows it ([[[#notation]]]). - Adapters normalize source sets, and MAY report the source duplicates they eliminate. A [=canonicalizing producer=] MUST reject duplicate members in a supposedly normalized source. - After canonical IDs are issued, every set array MUST be sorted by unsigned lexicographic comparison of the RFC 8785 UTF-8 serialization [[RFC8785]] of each complete member, ordering nested sets from the inside out before serializing the containing member. - A sequence MUST NOT be sorted. - `localeCompare()` and implicit locale collation MUST NOT be used in any protocol, identity, canonicalization, fixture, hash, signature or deterministic diagnostic ordering.
RFC 8785 sorts object member names by UTF-16 code units and leaves array order unchanged. Canonical VOWL's bytewise ordering of set members is a profile rule applied before RFC 8785, not a claim about RFC 8785 itself.
### No derived duplication {#no-derived-duplication} Every semantic and presentation attribute has one source of truth. The deliberate exception is the validated occurrence topology and its semantic reference sets, which address visual objects, support portable state, and are required in every profile; that addressing does not permit copying semantic attributes onto occurrences. A document MUST NOT contain derived duplicates, including: - class, property, datatype, node, language, namespace and individual counts; - language and base-IRI inventories; - per-record base IRIs; - reverse subproperty lists; - labels, comments, characteristics or annotations copied onto occurrences; - `anonymous`, `deprecated`, `external`, `inferred` and other derived flags; - both filter controls and their effective visibility result; and - internal section digests. An aggregate is primary rather than redundant only when its underlying detail is deliberately outside the profile; version 1 requires no such aggregate. ## Visual occurrences and projection {#projection} Occurrences represent the VOWL projection of the semantic model without copying its semantic fields. Other class expressions have no node glyph of their own. Each operator expression keeps its own node, so that different operators and their operand connections cannot collapse into one ambiguous composite symbol. Class nodes are generated as follows: 1. This is a visual grouping of explicitly connected names, not OWL semantic canonicalization. Inverse-expression members of an equivalence group remain in details, and do not become named property labels. ### Endpoint occurrence contexts {#endpoint-contexts} In this section, a generic class is a class-kind role over exactly `owl:Thing` or `rdfs:Resource`, whether its kind is `class` or `rdf-class`. - An ordinary class group or operator expression uses its context-free class node. - A datatype endpoint uses one `datatype-node` per pair of datatype role and `PropertyContext`, for named user datatypes as well as `rdfs:Literal`. - A generic class endpoint uses one `class-node` with that single target and a `ClassContext` containing the semantic targets of the opposite drawable class node. When the opposite endpoint is a datatype, the relation's `PropertyContext` is used instead, since there is no opposite class to anchor it to. - Two equal endpoint and context keys reuse one node, including for a self-loop; otherwise split nodes remain distinct. - For an operator, disjoint or subclass relation, the opposite class targets give the `ClassContext`. - Ordinary property contexts use the full equivalent-property partition. Restriction contexts use only the restriction's exact named property role, with its subclass construct as `scope`; they do not borrow the aliases of a global endpoint partition. These contexts make the fallback for a missing data-property domain explicit without inventing ontology identity. ### Edges and labels {#edges-and-labels} #### Property edges {#property-edges} One `property-edge` is created for each drawable property partition, subject to the inverse-pair replacement below. Its `from` is the partition's effective domain occurrence, and its `to` is the partition's effective range occurrence. #### Inverse edges {#inverse-edges} For each `inverse-properties` construct whose members are named object-property roles: 1. Locate the members' property partitions. For a singleton member set, use that same member on both sides of the pair. 1. The construct has an inverse glyph only when both partitions are drawable and their endpoint terms are exactly reversed. 1. Orient the pair by comparing the RFC 8785 UTF-8 serialization of each partition's sorted set of (subject IRI, role kind) tuples; the smaller side is `forward`. Equal sides are necessarily a self-loop. 1. The `inverse-edge`'s `from` is the effective domain occurrence of its `forward` partition, and its `to` is that partition's effective range occurrence. The `reverse` partition therefore runs from `to` to `from`, and equal sides produce the self-loop. 1. Create one `inverse-edge` per such construct, and omit the ordinary property edges of the partitions it represents. A partition involved in more than one explicit inverse pair can have several inverse occurrences, distinguished by their construct references. An inverse assertion that cannot satisfy these conditions remains in details, and any independently drawable ordinary property relation is kept. Endpoint inference MUST NOT be used to manufacture an inverse glyph. #### Subclass and disjoint edges {#subclass-and-disjoint-edges} For each `subclass` construct whose two terms are drawable, a directed `subclass-edge` is created. Its `from` is the endpoint occurrence of the construct's `sub` term, and its `to` is the endpoint occurrence of its `super` term ([[[#endpoint-contexts]]]).
This orientation is an accepted clarification ([[[#accepted-clarifications]]]).
For each `disjoint-classes` group: - enumerate the unordered pairs of distinct drawable member terms, create their endpoint occurrences using each other as context, and create one `disjoint-edge` per resulting endpoint pair; - a singleton normalized group, or a pair that collapses to one occurrence, produces a self-loop, preserving the retained assertion rather than deleting it; - identical endpoint pairs within one construct are deduplicated, and the semantic construct MUST NOT be expanded into separate pairwise constructs; and - undrawable members remain in details, and the drawing does not claim to display their part of the assertion. #### Operator edges {#operator-edges} Each drawable class operator's node is connected to the node of each drawable operand by an `operator-edge`. The edge's `from` is the operator's class-node occurrence, and its `to` is the drawable operand's node occurrence. Connections that land on the same class group for the same expression are deduplicated. Every operand remains in the expression record, including an undrawable one. A [=renderer=] MUST expose the complete expression in details and accessible summaries. A drawing that omits operands MUST indicate that the expression's details contain additional operands, using a derived cue rather than a new canonical field or an invented operand glyph. #### Restriction edges {#restriction-edges} A subclass restriction gets a `restriction-edge` only when all of these conditions hold: 1. `sub` is a named class or RDFS-class role; 1. `super` is an object or data minimum, maximum or exact cardinality expression; 1. its property is a named object or data property role, not an inverse expression; and 1. its normalized filler is exactly `owl:Thing` for an object restriction, or `rdfs:Literal` for a data restriction. Characteristics asserted on an inverse expression MUST NOT be transferred to its operand, and the characteristics of nonprincipal members remain in details. - Restriction labels keep their scoped cardinality treatment, rather than gaining a second, global property glyph. ### Projection matrix {#projection-matrix} Each retained role, expression and construct kind MUST have exactly one entry in a versioned, machine-readable projection matrix published with the profile. ### Externality {#externality} Externality is a lexical presentation classification, not ownership, membership in the imports closure, or retrieval provenance. It uses the root ontology IRI, the complete subject IRI, the namespace-key comparison below, and a closed set of built-in exemptions. - An anonymous root ontology, or an unnamed subject, is never classified as external. - A subject whose full IRI equals the root ontology IRI is local. - Membership in an imported ontology is not an externality test. The namespace key of an IRI [[RFC3987]] is computed as follows: 1. Parse the scheme, authority, path, query and fragment boundaries using the IRI grammar, without rewriting any component. 1. Let `trimPath` remove exactly one final `/` or `:` from a path, if present; it never trims the scheme delimiter, the authority or the query. 1. The root ontology's key is its original scheme and authority prefix, `trimPath` applied to its path, and its original query including `?` if present; its fragment, including `#`, is omitted. 1. A subject with a fragment has its key formed by the same rule. 1. For a subject without a fragment, locate the last `/` in its path, or, if there is none and the IRI has no authority, the last `:` in its path. If such a separator exists, discard it and the path text after it, including an empty final segment; otherwise keep the full path. Then apply `trimPath` to the remaining path, and concatenate the unchanged scheme and authority prefix, the path and the query. Keys are compared as exact strings, with the query retained and no URL normalization; a subject whose key differs from the root ontology's key is external, unless it is exempt. For example, `https://example.org/o#A` and `https://example.org/o/A` both have the key `https://example.org/o`, while `https://example.org/o/sub/A` has a different key; and for a root `urn:example:ontology`, the subject `urn:example:ontology:Class` has the root's key. ## Artifact profile {#artifact} The [=artifact profile=] binds the structural content of [[[#data-model]]] and its occurrences together with portable, static visualization state. This section defines that state and the label selection that renderers apply to every profile. The meaning of the display record's fields is specified in [[[#display-modes]]].
Consolidated from design section 15, projection contract B3 and B4, and the accepted [camera error precedence clarification](../specs/2026-09-30-canonical-vowl-camera-error-precedence.md), with requirement keywords added; no rule was added or removed. The visualization records below match `packages/vowl/schema/artifact.schema.json`.
### Static snapshot {#static-snapshot} An artifact is a portable, static visualization. It restores paused, and it binds: - one position for every positionable node and movable-label occurrence, including occurrences that are currently hidden; - an explicit pin for every placement; - the camera centre and zoom; - the effective set of hidden occurrences; - the effective label-selection mode; - the effective display-prefix map; and - the standardized VOWL display modes that change notation or semantic visual encoding: compact notation, node scaling and external colouring. An artifact MUST NOT carry force velocities, force parameters, alpha or convergence state, random state, timers, running or paused session state, DOM or SVG details, viewport dimensions, device-pixel ratio, CSS, themes, fonts, hover, focus, selection, search, editor mode, or open-panel state.
Force parameters are excluded even where an application persists them. Once exact positions are present, force parameters are instructions for a possible future layout run, not facts needed to reproduce the static artifact.
### Artifact grammar {#artifact-grammar} The artifact's required `visualization` is exactly `{placements: Set, camera: Camera, hidden: Set, labelSelection: LabelSelection, prefixes: Set, display: Display}`. | Record | Closed fields | | --- | --- | | Placement | `occurrence: O`, `position: Point`, `pinned: Boolean` | | Point | `x: Number`, `y: Number` | | Camera | `center: Point`, `zoom: Number`, which MUST be greater than zero | | IRI selection | `mode: "iri"` | | Untagged selection | `mode: "untagged"` | | Language selection | `mode: "language"`, `range: Text` | | PrefixBinding | `prefix: Text`, `iri: IRI` | | Display | `compactNotation: Boolean`, `nodeScaling: "uniform"` or `"direct-membership"`, `externalColoring: Boolean` | `LabelSelection` is exactly the three selection branches above. Every display value MUST be explicit; no omitted value takes its meaning from a WebVOWL preference, a device locale or a future application default. Structural-content documents contain none of these fields ([[[#envelope]]]). Converting a structural document into an artifact requires complete visualization state supplied by the caller; a [=canonicalizing producer=] MUST NOT choose a layout. ### Placements {#placements} - There MUST be exactly one placement for every positionable occurrence ([[[#labels-and-placements]]]), including hidden ones, and no placement for any edge. - Coordinates MUST NOT be inferred, quantized or filled with zero. - Placements are a set keyed by occurrence reference, not an ordered list of nodes. ### Coordinates and camera {#coordinates-and-camera} Positions and the camera centre use one dimensionless VOWL canvas coordinate system.
```json {"x": 0, "y": 0} {"center": {"x": 0, "y": 0}, "zoom": 1} ```
- Every coordinate and the zoom are finite IEEE 754 binary64 numbers. - `zoom` MUST be greater than zero. This is a numeric scalar-domain check: a finite zero or negative zoom fails with `NUMBER_INVALID` before graph or artifact-completeness validation ([[[#validation-order]]]). - Canonical input MUST NOT contain negative zero; an adapter MAY normalize a computed negative zero to positive zero before constructing the source. - Coordinates are not quantized; RFC 8785 [[RFC8785]] controls their number serialization. The camera centre is in canvas units. For a viewport whose centre is `(w / 2, h / 2)`, a point `(x, y)` projects to `(w / 2 + zoom × (x − center.x), h / 2 + zoom × (y − center.y))` before any renderer-specific styling. Viewport dimensions are inputs to rendering, not canonical state. A historical translation `(tx, ty)` at scale `z` converts to the centre `((w / 2 − tx) / z, (h / 2 − ty) / z)` only when the corresponding viewport is known ([[[#artifact-camera]]]). The scene restores paused. ### Effective visibility {#effective-visibility} `hidden` MAY contain any occurrence, and it MUST be closed under incidence: hiding a node hides its incident edges, and hiding an edge hides its labels. Hiding a label does not hide its edge. The state adapter computes this effective closure before calling the core, and a [=canonicalizing producer=] MUST reject an incomplete closure. The hidden set is the final visibility, not filter controls and not a second stored visibility result.
Storing the effective hidden set, rather than implementation-specific filter controls, prevents a filter setting and its derived visibility from becoming two sources of truth, and lets a different renderer reproduce the same selected scene.
### Label, prefix and language selection {#label-selection} A [=renderer=] MUST select the label of every occurrence as specified in this section, for every profile. Candidate selection and fallback are normative and independent of locale; candidates at the same precedence are resolved by canonical UTF-8 byte order, never by collation. There is no automatic English fallback and no application-preference default. #### Candidate labels {#label-candidates} The candidate labels of a target are the values of the retained `rdfs:label` annotation assertions on the target subject, restricted to language literals and typed `xsd:string` literals. Axiom-annotation labels and labels on unrelated occurrences are not candidates. Lexically equal candidates are deduplicated for selection only; the canonical assertion and anchor records are preserved. #### Grouped glyphs {#grouped-glyph-labels} - For a grouped class or property glyph, the principal named member is selected by local-before-external classification ([[[#externality]]]), then by the unsigned UTF-8 order of its complete IRI, then by its role-kind token. This choice is independent of canonical IDs, artifact coordinates, and whether external colouring is enabled. - The remaining equivalent names are displayed as an alias list, ordered by their full subject IRIs in unsigned UTF-8 order and then by role kind, not by the selected human-language text. Truncation to fit the available pixels is renderer state, and MUST NOT change the underlying labels or bytes. - The principal member also determines the grouped glyph's class or property kind and its characteristic treatment; each remaining member's exact characteristics stay available in details. - An inverse edge applies this rule separately in each of its two directions, and asserts no union of different members' characteristics. - An anonymous class has its own annotation candidates, and an operator has its fixed `union`, `intersection` or `complement` meaning and the corresponding VOWL symbol. #### Selection modes {#selection-modes} - `mode: "iri"` selects the full IRI of a named target, bypassing labels and prefixes. For a target with no IRI it selects the applicable fixed kind name, `anonymous class`, `union`, `intersection` or `complement`, never the producer handle. - `mode: "untagged"` selects the least candidate typed `xsd:string` value by its complete RFC 8785 UTF-8 bytes. When there is none, the IRI-derived fallback applies. - `mode: "language"` uses a single, lowercased RFC 4647 basic language range [[RFC4647]], including `*` but excluding embedded wildcards and quality weights. Language-range validation is distinct from language-tag validation; both use the ASCII lowercasing policy of [[[#literals]]]. - Exact tag lookup is performed at each RFC 4647 lookup truncation step, removing a trailing singleton together with its extension or private-use subtag as RFC 4647 specifies. A less specific request MUST NOT be expanded into an arbitrary more specific tag. - At the first matching tag, the least complete literal by RFC 8785 UTF-8 bytes is chosen. - The range `*` goes directly to the default. - The default is the untagged selection, and then the IRI-derived fallback; English is not an implicit preferred language. For example, `zh-hant-tw` tries that tag, then `zh-hant`, then `zh`, while `en` does not arbitrarily choose between `en-gb` and `en-us` when only those exist. #### IRI-derived fallback {#iri-fallback} The IRI-derived fallback is deterministic: 1. For exactly `http://www.w3.org/2002/07/owl#Thing`, `http://www.w3.org/2002/07/owl#Nothing`, `http://www.w3.org/2000/01/rdf-schema#Resource` and `http://www.w3.org/2000/01/rdf-schema#Literal`, use the fixed built-in names `Thing`, `Nothing`, `Resource` and `Literal`. 1. Otherwise, among the effective prefix bindings that are exact lexical prefixes of the IRI and leave a nonempty suffix containing no `:`, `/`, `#` or whitespace, choose the longest IRI prefix, measured in Unicode scalar values, breaking ties by the unsigned UTF-8 order of `prefix`; display `prefix:suffix`. 1. Otherwise, use the nonempty lexical suffix after the last `#`, `/` or `:`, without percent-decoding it. 1. If that suffix is empty, use the full IRI; for an unnamed target, use its fixed kind name. For this rule, whitespace is exactly U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000; a runtime's changing Unicode or regular-expression tables do not define it. #### Prefix bindings {#prefix-bindings} - A prefix name is either empty or matches `[A-Za-z][A-Za-z0-9_-]*`. Prefix names MUST be unique, and they are case-sensitive. - An empty prefix displays as `:suffix`. - Different prefixes MAY bind the same IRI; the tie-break of the IRI-derived fallback resolves the display without deleting an active binding. - The map stores the effective display bindings supplied by the state adapter, not a copy of every namespace declaration in the source syntax. Structural data uses full IRIs, and raw prefixes from Turtle, RDF/XML, Functional Syntax or JSON-LD do not survive merely because they occurred in a source document. - Shortening text never changes a semantic IRI. #### Fixed label wording {#fixed-label-wording} - Subclass labels use the fixed phrase `Subclass of`, and operator symbols and cardinality spellings follow [[[#edges-and-labels]]]. - Property and inverse-direction labels use the names of their selected property members. - Restriction labels use the selected name of their exact property and the cardinality spelling of [[[#restriction-edges]]]. - Annotation labels and aliases are not serialized again into occurrences. ## Compatible-artifact profile {#compatible-artifact} The [=compatible-artifact profile=] binds the structural content and complete visualization of the [=artifact profile=] together with portable qualifications: the source documents and imports of the view, the decisions and assessments that qualify its interpretation, and the source RDF statements that it retains without interpreting them. ### Admission {#compatible-admission} A [=canonicalizing producer=] and an [=exact decoder=] of this profile apply the snapshot, input-size, UTF-8, Unicode, number and duplicate-member rules of [[[#encoding]]], and stages 1 to 3 and the common envelope checks of stage 4 of [[[#validation-order]]]. After selecting the profile, they MUST check the rest of their input in this order, in place of the remaining stages, and report the first failure that it determines: 1. **Closed fields and scalar domains.** Visit the input parents first: the members of each object in the unsigned UTF-16 code-unit order of their names, and the elements of each array in index order. At each object, check that it is an object, then its missing members and then its unknown members, each in name order; then validate each present member completely, in name order, before the next. A member's JSON type precedes its token alternatives, scalar domain and collection bounds, and an array's shape and collection bounds precede its elements. A discriminated object needs a string `kind` that selects a listed branch before its other members are checked. These failures use `DOCUMENT_REQUIRED_FIELD`, `DOCUMENT_UNKNOWN_FIELD` and `DOCUMENT_TYPE`, and, after a scalar's JSON type, the named scalar codes such as `IRI_INVALID` and `DECIMAL_INVALID`. 1. **Inherited checks.** The structural graph, meaning and projection checks, and then the complete visualization checks, of stages 5 to 7 of [[[#validation-order]]]. 1. **Qualifications**, in the order of [[[#qualification-checks]]]. 1. **Mapping and issuance.** Map the document ([[[#compatible-rdf]]]), refine and label the dataset ([[[#compatible-refinement]]]), and issue IDs, sort sets and serialize ([[[#compatible-issuance]]]). An [=exact decoder=] then compares the resulting bytes with its input, and MUST fail with `NON_CANONICAL_BYTES` on any difference, without returning the sorted or repaired document. Because each member is validated completely before the next, an invalid earlier member can precede a later member's JSON-type error. Normalized-source admission follows the same order, over the envelope without `profile`. #### Qualification checks {#qualification-checks} The qualification checks visit each collection's records in complete-member RFC 8785 UTF-8 order, after sorting each record's sets recursively, using the handles as supplied. This ordering issues no IDs and repairs nothing. 1. Index the records of the five structural collections, and then of `documents`, `imports`, `entries`, `sourceNodes` and `sourceStatements`. A qualification ID that is empty or equals the ID of another primary record MUST fail with `IDENTIFIER_INVALID`, and so, when decoding, MUST one other than its category's prefix followed by a decimal integer spelled as [[[#noncanonical-input]]] specifies. 1. A set of documents without exactly one root MUST fail with `DOCUMENT_TYPE`. 1. In `imports`, then `entries`, then `sourceStatements`, two records whose complete payloads are equal apart from `id`, with their nested sets sorted, MUST fail with `NORMALIZATION_INVALID`. 1. For each source statement, its `subject`, `object` and `graph` in that order: an anonymous term whose node is missing from `sourceNodes`, or belongs to another document, MUST fail with `REFERENCE_INVALID`. Then a source node that no statement uses MUST fail with `NORMALIZATION_INVALID`. 1. An import whose `targetDocument` presence does not match its `state` MUST fail with `DOCUMENT_TYPE`. 1. An entry with an empty `code`, a rule outside [[[#compatible-rules]]], a dimension that its detail does not allow, or a failed scope-code, property or headers condition of [[[#compatible-details]]] MUST fail with `DOCUMENT_TYPE`. 1. Visit the qualification fields parents first, members in name order and elements in index order. A typed reference whose target is missing or of the wrong category MUST fail with `REFERENCE_INVALID`, and a set with two equal complete members MUST fail with `NORMALIZATION_INVALID`. The rank of a qualification ID is verified only by the final byte comparison. In this section, `J(x)` is ECMAScript's well-formed `JSON.stringify(x)` without whitespace, `U` is UTF-8 encoding, and `H` is SHA-256 written as 64 lowercase hexadecimal digits. `J` frames the refinement only; the document is still serialized by RFC 8785. The base dataset is a set of default-graph triples whose predicates are IRIs, none of them in the namespace `https://haddenindustries.com/ontology/vowl/compatible-mapping/v1#`. A base dataset that is not MUST fail with `DEPENDENCY_FAILURE`, and never selects another mapping. An implementation that holds the dataset as a list of triples MUST treat it as a set before refining it; a repeated triple is not a second permitted mapping. 1. For each distinct ground term, prepare `["term", H(U(J(key)))]`, where the key of a named node is `["iri", iri]` and that of a literal is `["literal", lexical, datatypeIRI, language]`. Every literal of the base dataset is typed, so its `language` is the empty string, never absent or `null`. 1. List the triples incident to each blank node: a triple that mentions the node twice is listed once for it, and a triple that connects two different blank nodes is listed for each of them. Every node's initial colour is the empty string, and the initial number of distinct colours is one if there are blank nodes, and otherwise zero. 1. In each round, the key of a term in a triple incident to node `b` is `["self"]` for `b`, `["blank", c]` for another blank node whose preceding colour is `c`, and its prepared key for a ground term. Each incident triple becomes the string `J([subjectKey, predicateKey, objectKey])`, and the strings are sorted by unsigned UTF-16 code units, a prefix before any longer string. 1. The node's next colour is `H(U(J([c, s])))`, where `c` is its preceding colour and `s` the array of its sorted strings. `s` is an array of strings, not of nested arrays, so the quotation marks and backslashes inside them are escaped again. Every node in a round reads only the preceding round. 1. Adopt the round's colours and count their distinct values. Stop when the count is not greater than the preceding count, and otherwise begin another round; the colours of the stopping round are final. With no blank nodes, no round runs and nothing is appended. 1. Keep every base triple, and append one default-graph triple for each blank node, whose predicate is `https://haddenindustries.com/ontology/vowl/compatible-mapping/v1#color` and whose object is the node's final colour, in lowercase, as an `xsd:hexBinary` literal. Then label the complete augmented dataset with RDFC-1.0 and SHA-256 [[RDF-CANON]], as [[[#canonicalization-algorithm]]] and [[[#rdfc-work]]] specify. Removing the colour triples recovers the base dataset, so refinement cannot erase a distinction that the mapping makes, and renaming blank nodes or reordering triples changes no colour, round or stopping point. Equal colours do not establish isomorphism, and never permit skipping RDFC-1.0 or merging nodes: nodes that stay symmetric keep equal colours, and their deep comparisons remain bounded by [[[#rdfc-work]]].
The deep-comparison allowance of [[[#rdfc-work]]] is charged on entry to each recursive call, so a dataset that needs too many calls fails however fast its hashing is. Refinement separates most blank nodes before labelling: refined, a path of four blank nodes has four colours after three rounds and needs no deep comparison, while unrefined it needs at least one.
### ID issuance and encoding {#compatible-issuance} From the canonical identifier map of the augmented dataset, a [=canonicalizing producer=] and an [=exact decoder=] MUST issue IDs as [[[#id-issuance]]] specifies, over the ten categories of [[[#compatible-rdf]]]: - each category is sorted by the numeric ordinal of its `c14nN` labels, and each record receives its category's prefix followed by its zero-based rank; - auxiliary nodes take part in labelling, but receive no IDs; - every declared primary ID and reference is replaced by its issued ID, references from qualifications to structural records included, and every other string is kept, even one that resembles an ID; - every set is sorted inside out by the complete-member RFC 8785 UTF-8 order of [[[#collections]]]; and - the document is serialized as its [=canonical encoding=]. ### Resource accounting {#compatible-limits} Although they receive canonical IDs, the records of the qualification collections count toward `embeddedValues` while the input is snapshotted or tokenized, like any other embedded object, and not toward `primaryRecords`, which counts only the five structural collections ([[[#limits]]]). The refinement counts toward the limits of [[[#limits]]], and reports them with their codes: - each entry of a node's incident list counts one toward `embeddedValues` when the list is built, and one in every round, including where the digest of an equal signature is reused; - each appended colour triple counts one toward `rdfQuads`; - each time it prepares the key of a ground term, it first counts the key's UTF-8 JSON length toward `totalStringBytes`; and - before a round builds a node's signature, it fails if `1024 + 2048 × n` bytes, for the node's `n` incident triples, exceed `totalStringBytes`; these bytes bound the round's scratch strings, and are not added to the count. Cancellation and the deadline are checked before and after every digest. An implementation MAY compute the refinement differently only where both its successful bytes and this accounting stay the same.
None of these counts meters process memory or JavaScript object overhead.
## Internal RDF mapping and canonical identifiers {#canonicalization} The internal RDF mapping and the issuance of canonical IDs are protocol rules, even though they are private operations inside an implementation: RFC 8785 cannot compensate for a difference in either stage. This section defines the canonicalization algorithm, the internal RDF dataset that is labelled, and the rule that turns RDFC-1.0 labels into [=canonical IDs=].
Consolidated from design section 18, including 18.1 and 18.2, and core contract A6, with requirement keywords added; no rule was added or removed. The evidence and fixture obligations of design sections 18.1 and 18.2 move to [[[#schemas-and-corpus]]], and the bounded work controls of step 4 are specified in [[[#errors]]]. The reference implementation's mapping, RDFC-1.0 invocation and ID issuance match this section.
### Canonicalization algorithm {#canonicalization-algorithm} For the selected profile, a [=canonicalizing producer=] MUST perform these steps in order: 1. **Snapshot and validate the source.** Accept only acyclic plain records, dense arrays, JSON primitives and closed fields. Reject non-finite numbers, negative zero, lone surrogates, noncharacters that I-JSON prohibits [[RFC7493]], dangling references, invalid IRIs, invalid language tags, wrong collection kinds, unknown fields and conflicting records. 1. **Normalize scalar forms.** Preserve Unicode and IRI spelling, lowercase valid language tags and ranges, and require canonical decimal strings where they are specified. Validate the adapter's normalized endpoints, signature closure and occurrence generation against [[[#normalization]]] and [[[#projection]]], without silently repairing an unnormalized structural graph. Unicode normalization, IRI percent-decoding, IRI case folding and general semantic inference MUST NOT be performed. 1. **Build the internal RDF dataset** ([[[#internal-rdf]]]). Map every fact of the selected profile injectively, using repeated predicates for sets and position-bearing structures for sequences, and include the profile identifier so that labelling is domain-separated. The dataset includes every primary node, auxiliary node, empty collection and artifact fact. This mapping is internal; it does not make the public JSON an RDF serialization. 1. **Run RDFC-1.0** [[RDF-CANON]]. Use the algorithm name `RDFC-1.0` with SHA-256 as its message digest, reject the deprecated `URDNA2015` alias, honour cancellation, and apply the bounded work controls of [[[#errors]]]. There MUST be no noncanonical fallback. 1. **Issue category-local IDs** ([[[#id-issuance]]]), replacing every source handle. 1. **Build the closed document.** Emit the required fields, omit forbidden derived fields ([[[#no-derived-duplication]]]), and sort every set ([[[#collections]]]). 1. **Validate the result.** Recheck the closed schema, reference integrity, uniqueness, set ordering, sequence rules, numeric domains and profile invariants. 1. **Return the document** as an immutable value. Encoding is a separate operation over this document ([[[#encoding]]]).
In JavaScript, step 1 also rejects accessors, `toJSON` methods, symbol keys and values, functions, `undefined`, `BigInt` values and sparse arrays. The reference implementation does not claim to sandbox a hostile JavaScript `Proxy`.
### Internal RDF dataset {#internal-rdf} #### Vocabulary and graph framing {#rdf-vocabulary} The mapping vocabulary has exactly this base: ```text https://haddenindustries.com/ontology/vowl/canonical-mapping/v1# ``` In this section, `m:` abbreviates that base for notation only. It is a newly formulated algorithm vocabulary, not a claim that these IRIs are deployed or that an OWL ontology has adopted them. It is published with the profile's specification bundle, and an implementation MUST NOT dereference it while canonicalizing. After a stable release, changing this base or any template requires a new canonical profile ([[[#versioning]]]). The complete vocabulary is `m:root`, `m:Object`, `m:Subject`, `m:Role`, `m:Expression`, `m:Construct`, `m:Occurrence`, `m:Set`, `m:Sequence`, `m:Slot`, `m:member`, `m:slot`, `m:index`, `m:value`, `m:token`, `m:binary64`, and the predicate family `m:field/NAME`. `NAME` ranges over the exact canonical field names of [[[#data-model]]], [[[#projection]]] and [[[#artifact]]], including the envelope fields `profile`, `structural` and `visualization` and excluding the primary `id`. Operation options, limits, errors, diagnostics and migration resolutions do not define field predicates. `rdf:type`, `xsd:string`, `xsd:boolean` and `xsd:nonNegativeInteger` use their standard namespace IRIs. All triples are in the default graph, and there are no named graphs. The document root is the fixed named node `m:root`, of type `m:Object`, whose ordinary `profile` field points to the selected canonical profile identifier. #### Allocation {#rdf-allocation} - Every referenceable subject, role, expression, construct and occurrence MUST map to exactly one distinct primary blank node, typed `m:Subject`, `m:Role`, `m:Expression`, `m:Construct` or `m:Occurrence` according to its containing collection. A subject's IRI is a fact about the subject; it does not replace the primary node used for ID issuance. - Every embedded object and every collection receives a fresh auxiliary blank node, and every sequence item additionally receives a fresh slot node. Auxiliary nodes MUST NOT be shared between equal embedded values, or according to object identity in the producer. - No node is created for an absent optional field. - Blank-node labels used during construction are arbitrary handles with no semantic significance. - Every allocated node MUST be reachable from `m:root` through field, member, slot or reference edges; unused allocations are not part of the dataset. Auxiliary nodes, for literals, nested values, annotations, collection containers, sequence slots, ontology metadata and artifact state, receive no public category IDs, but their facts take part in whole-profile labelling. #### Templates {#rdf-templates} These templates apply recursively to every field of [[[#data-model]]], [[[#projection]]] and [[[#artifact]]]. Distinctions that VOWL normalization explicitly eliminates are outside that claim; every retained distinction MUST be recoverable from the mapped dataset.
##### Recovery argument {#rdf-recovery} Starting at `m:root`, field predicates recover each object's members and their declared types. Node types distinguish records, embedded objects, sets, sequences and slots. Absent edges and present empty containers differ; slot indices recover order and repetition; and boxed literal fields preserve lexical and datatype distinctions. References recover a graph of distinct primary nodes, not the spelling of producer handles. Fresh auxiliary allocation gives each embedded value a single ownership position, so sharing in the producer cannot introduce additional graph facts. By structural induction over embedded values and the finite expression graph, the inverse recovers the normalized model up to primary-handle renaming and set permutation. As a result: - absent optional fields, present empty objects, empty strings, and empty sets and sequences remain distinguishable where the grammar permits them; - tokens, IRIs and strings have distinct encodings, and literal lexical values and normalized language tags are preserved; - sets carry no encounter order, while sequences keep their order, length and repeated values; - subject and role relationships, punning, recursive expression references, construct arguments, split contexts, occurrence endpoints and assertion anchors remain distinguishable; - annotations keep their full predicate IRIs, value discriminators, nested sets and attachment to the correct pre-aggregation assertion; and - structural topology is labelled in both profiles, positions, pins, camera, visibility, prefix bindings, label selection and display modes in the artifact profile, while excluded provenance and runtime state never enter the dataset. This is a design-level argument; implementations must still check the templates and their counterexamples independently ([[[#schemas-and-corpus]]]).
### Category-local ID issuance {#id-issuance} The RDFC-1.0 identifier issuer produces canonical blank-node identifiers with the prefix `c14n` and a zero-based counter [[RDF-CANON]]. The N-Quads `_:` marker is syntax, not part of `N`, and a library's map wrapper MUST NOT affect the interpretation. 1. Partition only the primary record nodes into the five categories below. The partition MUST NOT depend on a producer's ID spelling or on an RDF library's iteration order. 1. Sort each category by increasing numeric `N`, not lexicographically by `c14nN`, comparing integers exactly without floating-point rounding. 1. Assign each record its category prefix followed by its zero-based rank, in plain decimal without leading zeros. Ranks restart at zero for each category and leave no gaps. 1. Replace all references consistently, including occurrence contexts and artifact placements, and then order set arrays as [[[#collections]]] specifies; set ordering is a separate rule from ID issuance. | Primary record category | Canonical ID prefix | | --- | --- | | Subjects | `s` | | Roles | `r` | | Expressions | `x` | | Constructs | `c` | | Occurrences | `o` | For example, roles labelled `c14n2` and `c14n10` receive `r0` and `r1`, even if the map yields `c14n10` first. - Auxiliary nodes may occupy intervening RDFC-1.0 ordinals, but they receive no canonical IDs and create no gaps in the category ranks. - An absent label, a primary node assigned more than one label, or a conflicting category MUST be treated as an error; it is never a tie to be broken by input order. - The order of canonical N-Quads lines MUST NOT be used as an ID issuance order. - Under graph symmetry, the ID assigned to a source handle is not a durable identity; conformance concerns the complete canonical document after every reference has been replaced. - The private RDF dataset and its auxiliary labels are conformance artifacts, not fields of the canonical document. ## Encoding and exact decoding {#encoding} This section defines the byte encoding of an admitted document, the exact decoding that verifies bytes without repairing them, and the order in which a [=canonicalizing producer=] and an [=exact decoder=] report the first failure of invalid input. ### Canonical encoding {#canonical-encoding} The canonical encoding of an admitted document is its RFC 8785 serialization [[RFC8785]] in UTF-8 [[RFC3629]], with no byte-order mark, no trailing newline and no other bytes. A [=canonicalizing producer=] MUST complete the validation of [[[#canonicalization-algorithm]]] before it serializes a document, so that no coercion by a serializer can affect the bytes. The serialization itself can come from any conforming RFC 8785 implementation. A [=canonicalizing producer=] or [=exact decoder=] that offers encoding as a separate operation MUST encode only a document that the same implementation instance admitted through a successful canonicalization or exact decoding. It MUST fail with `DOCUMENT_NOT_ADMITTED` for any other value, even one whose shape is plausible, and MUST return newly allocated bytes from each encoding. Admission is state that the implementation holds; it is never a member of the document.
In JavaScript, validation has to precede any serializer that could invoke `toJSON`, omit an unsupported object property, turn an unsupported array element into `null`, collapse a sparse array or serialize negative zero. The reference implementation's `encode` is synchronous and accepts only a deeply frozen document returned by `canonicalize` or `decode` of the same module instance, so a copy of an admitted document, such as one cloned for rendering in another thread, is not admitted.
### Exact decoding {#exact-decoding} An [=exact decoder=] MUST perform these steps in order, and MUST return a document only after every step has succeeded: 1. **Check the input size.** Compare the input's length with the input-byte limit ([[[#errors]]]) before allocating any decoded text. 1. **Decode UTF-8.** Decode the input as UTF-8 [[RFC3629]] with fatal error handling, failing with `JSON_INVALID_UTF8` rather than replacing an ill-formed sequence, and then fail with `JSON_BOM` if the input begins with a byte-order mark. 1. **Tokenize and validate the JSON text** [[RFC8259]]. Fail with `JSON_SYNTAX` where the text does not match the JSON grammar, enforce the nesting, string and collection limits of [[[#errors]]] as tokens are read, and reject a duplicate member name ([[[#duplicate-members]]]) before either binding can be overwritten. 1. **Construct the JSON value** only from the validated tokens, rejecting any string that is not [=Unicode-valid=] ([[[#unicode-admission]]]) and any number outside the admitted domain ([[[#number-admission]]]). 1. **Validate the document.** Select the profile whose identifier is exactly the value of `profile`, failing with `PROFILE_UNKNOWN` if there is none, and validate the closed grammar and semantic constraints of that profile, including references, duplicate-free sorted sets, sequences, scalar spelling and the profile's invariants. 1. **Reconstruct and recanonicalize.** Reconstruct the profile's normalized source, using the document's IDs only as temporary handles; rerun the internal RDF mapping, RDFC-1.0 labelling and ID issuance of [[[#canonicalization]]]; and compare the resulting canonical document with the supplied one. 1. **Compare bytes.** Produce the [=canonical encoding=] of the verified document and compare it byte for byte with the input. 1. **Return the document**, immutable and admitted. An exact decoder MAY combine steps 3 and 4 in one tokenizing parser. It MUST NOT supply a default, repair, coerce or strip a value, ignore an unknown member, or return a repaired document. A difference found in step 6 or 7 MUST fail with `NON_CANONICAL_BYTES`: reconstruction verifies the input, and is never a repair path.
RFC 8785 never sorts arrays, so a set in the wrong order is rejected by semantic validation, not by the serializer. The byte comparison of step 7 rejects noncanonical whitespace, member order, number spelling and escaping, as well as trailing bytes.
### Lexical admission {#lexical-admission} #### Duplicate member names {#duplicate-members} An [=exact decoder=] MUST detect a member name that repeats within one object while it tokenizes, and MUST fail with `JSON_DUPLICATE_MEMBER` before either binding can be overwritten. Names are compared after JSON escape processing, with no case folding or Unicode normalization: `"profile"` and `"\u0070rofile"` are duplicates in the same object, while the same name in different objects is not a duplicate. Equal and conflicting duplicates both fail, at every depth, including inside nested annotations and artifact state. This enforces the restriction on duplicate member names that [Section 3.1](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.1) of [[RFC8785]] places on its input, before any information is lost.
An ordinary parser that keeps one binding, such as JavaScript's `JSON.parse`, cannot detect duplicates, and neither can a reviver or schema validation applied to its result. The byte comparison of [[[#exact-decoding]]] would reject a duplicate that such a parser had collapsed, but only as a generic mismatch, without the duplicate-specific error and location. Conversely, duplicate-safe parsing and RFC 8785 serialization do not prove that a document uses the required IDs: reconstruction is needed even for compact JSON with sorted members.
#### Unicode admission {#unicode-admission} A string is Unicode-valid when it contains no lone surrogate and none of the noncharacters that I-JSON prohibits [[RFC7493]]: U+FDD0 to U+FDEF, and the code points from U+FFFE to U+10FFFF whose last four hexadecimal digits are FFFE or FFFF. An escaped surrogate pair such as `\ud83d\ude00` denotes one scalar value, which is checked after decoding; an escaped lone surrogate such as `\ud800` is not Unicode-valid. Every string in a [=Canonical VOWL document=], member names included, MUST be [=Unicode-valid=]. A [=canonicalizing producer=] and an [=exact decoder=] MUST fail with `UNICODE_INVALID` on any string or member name of their input that is not. Every other character is retained, including distinctions that Unicode normalization would remove and control characters, among them those that JSON text can carry only as escapes. #### Number admission {#number-admission} A JSON number is admitted when its binary64 value is finite and not negative zero, which is the domain of `Number` ([[[#notation]]]). An [=exact decoder=] MUST fail with `NUMBER_INVALID` while constructing the value for any other number, such as `-0`, `-0.0e0` or `1e400`, and a [=canonicalizing producer=] MUST fail with `NUMBER_INVALID` for any such number in its input. An admitted number with a noncanonical spelling, such as `1.0` or `1E2`, fails only at the byte comparison, with `NON_CANONICAL_BYTES`. Field-specific numeric domains, such as the strictly positive camera zoom, are checked later ([[[#validation-order]]]). ### Noncanonical input {#noncanonical-input} Every [=canonical ID=] in a [=Canonical VOWL document=] is its category prefix followed by `0` or by a decimal integer without a leading zero, and the IDs of each category are its contiguous ranks ([[[#id-issuance]]]). An [=exact decoder=] MUST fail with: - `ID_INVALID` for an ID that is not spelled this way; - `ID_DUPLICATE` for an ID that identifies more than one record; and - `NON_CANONICAL_BYTES` for validly spelled IDs with incorrect ranks or assignments, for an otherwise valid set in the wrong order, and for a noncanonical scalar spelling. A [=canonicalizing producer=] accepts arbitrary unique handles and any set order in a [=normalized source model=]; neither is an error in source input. ### In-memory input {#in-memory-input} A [=canonicalizing producer=] that accepts its source as in-memory values rather than bytes MUST take a snapshot of the complete input before the operation first suspends asynchronously, so that a later change to the input cannot affect the result. The snapshot copies by value each occurrence of an embedded value that the input shares between positions, because sharing is not semantic identity ([[[#source-model]]]). The producer MUST fail with `SOURCE_UNSAFE_VALUE` on input that is not plain data, such as a cyclic value, an accessor property, or a value of a type that JSON lacks, like `undefined`, a function, a symbol or a big integer. A number that JSON cannot represent, such as NaN or an infinity, is plain data that fails number admission instead ([[[#number-admission]]]). While taking the snapshot, it MUST also check each member name and string for Unicode validity ([[[#unicode-admission]]]) and each number against the admitted domain ([[[#number-admission]]]), so that these failures are reported with the snapshot at the start of stage 4 ([[[#validation-order]]]), before the closed field sets and every other scalar domain.
A source whose `structural` record has an unknown member `aaa` and a subject IRI containing a lone surrogate fails with `UNICODE_INVALID`, although `aaa` precedes `subjects` in member order.
Besides the rejections noted in [[[#canonicalization-algorithm]]], the reference implementation accepts only records whose prototype is `Object.prototype` or `null` and ordinary dense arrays, with only own enumerable data properties. It inspects property descriptors without invoking getters, and rejects accessors, symbol keys, extra array properties and nonenumerable record fields instead of ignoring them; an array's `length` is the only exception.
### Validation order {#validation-order} A [=canonicalizing producer=] and an [=exact decoder=] MUST check their input in these stages, in order, and MUST report the first failure that the order determines. A check that does not apply to an operation's input is skipped: for example, stage 3 applies only to bytes. 1. The operation and its options, then an already-aborted cancellation signal. 1. The kind of input, then the input-byte limit. 1. The fatal UTF-8 and byte-order-mark checks; then JSON grammar, decoded member names, [=Unicode-valid=] decoded strings, finite JSON numbers other than negative zero, and lexical limits, in token encounter order. 1. For in-memory input, the safety of its plain-value snapshot, including the Unicode and number checks made while taking it ([[[#in-memory-input]]]). When decoding, the envelope checks common to every profile, in this order: the document is an object; it has the members `profile` and `structural`; `profile` is a string and `structural` an object; and `profile` is a known profile identifier. Then closed field sets and scalar domains. 1. Primary IDs, reference existence, reference target categories, expression cycles and structural uniqueness. 1. Assertion support, normalized endpoints and signature closure, and exact occurrence projection. 1. Artifact placement and visibility completeness, and the camera and placement invariants. 1. RDFC-1.0 work and cancellation, ID issuance, canonical set ordering, document comparison and exact byte comparison. For byte decoding, Unicode and number admission therefore precede the envelope checks, and every other field-specific scalar domain is checked at stage 4. The strictly positive camera zoom ([[[#coordinates-and-camera]]]) is one of those numeric domains: a finite zero or negative zoom fails with `NUMBER_INVALID` before graph or artifact-completeness validation. Placement coverage, the incidence closure of the hidden set and the other structured artifact invariants remain at stage 7. Within an object, checks MUST follow the unsigned UTF-16 code-unit order of member names, and within an array, the index order in which its elements were supplied. At one location, required members are checked first, then forbidden members, JSON types, scalar domains, references and semantic constraints, in the stage order above. This fixes the first error for a given input value; it does not fix the same JSON Pointer for every permutation of an invalid set. A [=canonicalizing producer=] or [=exact decoder=] that observes cancellation or an expired deadline MUST stop before its next content check. Such an outcome depends on timing, not on the input, and is not canonical content. Stages 1 to 3 and the common envelope checks of stage 4 apply to every profile. After it selects the [=compatible-artifact profile=], a decoder follows that profile's own candidate schedule ([[[#compatible-artifact]]]) in place of the remaining stages.
Decoding `{"profile":"\ud800"}` fails with `UNICODE_INVALID`, although the document also lacks `structural` and names no known profile.
Within `visualization`, the member `hidden` precedes `placements`, which precedes `prefixes`. An incomplete hidden-set closure is therefore reported before a missing placement, and both before a repeated prefix name.
#### Failure positions {#failure-positions} Each stage-3 failure has a failure position, a byte offset in the input: - for JSON grammar, the first byte that cannot continue a JSON text, or the input's length if the input ends before its JSON text is complete; - for a duplicate member name, the closing quotation mark of the repeated name; - for a string that is not [=Unicode-valid=], the last byte that represents a prohibited code point or lone surrogate: the code point's last byte when it is raw, the last hexadecimal digit of its escape when it is escaped, and the last digit of the second escape when an escaped surrogate pair denotes it; - for a number outside the admitted domain, the first byte after the number, or the input's length if the number ends the input; and - for a lexical limit, the opening bracket or brace that takes the nesting depth or a count of values past its limit, or the last byte of the character or escape that takes the length of a string, or the total of all strings, past its limit. An [=exact decoder=] MUST report the stage-3 failure with the smallest [=failure position=]. When several failures share that position, it MUST report the first of them in this order: JSON grammar, decoded member names, Unicode-valid decoded strings, numbers, lexical limits.
- `[1 "\ud800"]` fails with `JSON_SYNTAX`: the misplaced quotation mark precedes the lone surrogate. - `[-0x]` fails with `JSON_SYNTAX`: the number and the grammar both fail at `x`, and grammar comes first. - `[-0]` fails with `NUMBER_INVALID`, at `]`. - `{"a":"\ud800\x"}` fails with `UNICODE_INVALID`: the escape of the lone surrogate ends before the invalid escape `\x`.
### Schemas and semantic validation {#schema-validation} The JSON Schema 2020-12 [[JSON-SCHEMA-2020-12]] schemas of [[[#schemas-and-corpus]]] are a mechanical translation of the closed tables of this specification: discriminated `oneOf` branches, exact required members, closed composed objects, and explicit array item types and cardinalities. Schema validity alone does not make input valid. A [=canonicalizing producer=] and an [=exact decoder=] MUST check the ordered invariants of [[[#validation-order]]], and MUST NOT rely on generic `uniqueItems` or on implementation-dependent `format` handling in place of typed record identity, IRI and language-tag validation, or graph verification. ## Errors and resource limits {#errors} This section defines how operations fail: the error object, the stable error codes, the translation of library failures, the resource limits that bound every operation, and cancellation. The order in which failures are reported is specified in [[[#validation-order]]].

### Failing closed {#failing-closed} Every operation of a [=canonicalizing producer=], [=exact decoder=], [=OWL mapping adapter=] or [=migration adapter=] MUST either succeed completely or fail with a single error. It MUST NOT return partial output, a repaired result or the result of a fallback algorithm. [[[#host-limits]]] describes the one failure that no operation can report. ### Error object {#error-object} A [=canonicalizing producer=], [=exact decoder=], [=OWL mapping adapter=] or [=migration adapter=] MUST report each failure as an error that carries: - `code`, one of the stable codes of [[[#error-codes]]] or of an adapter section; - `message`, text for people, which is not part of the contract; - optionally, `pointer`, a JSON Pointer [[RFC6901]] into the source or the document, wherever the failure has a value to point to; - optionally, `details`, bounded structured data that MAY contain `byteOffset`, `limit`, `maximum`, `actual` or a stage token; and - optionally, `cause`, the failure that led to this one. An implementation MUST NOT copy unbounded input values or stack traces into an error's serialized `details`. A lexical failure MAY report its byte offset as `details.byteOffset`, without echoing unbounded input. Codes and locations are the contract; neither an error's `message` nor the text of a library's own error is. The in-process interface does not use HTTP Problem Details [[RFC9457]]; an HTTP adapter MAY map these errors to it separately.
The reference implementation throws a single error class, `VowlError`, with these properties; its `details` object is frozen.

### Host limits {#host-limits} An unbounded limit hands the bound to the host runtime. An operation that reaches a limit of its host runtime rather than a configured one, such as its call stack or the largest string, array or buffer it can allocate, MUST fail with `HOST_RESOURCE_LIMIT`, whose `details.resource` is `callStack` or `allocation`. Cancellation and an expired deadline take precedence, as they do for configured limits. Raising a configured limit cannot avoid a host limit. Memory exhaustion that ends the worker or process cannot be reported, and is outside the guarantee of [[[#failing-closed]]].
JavaScript engines expose no error type for these failures. The reference implementation recognizes them by the messages that V8, JavaScriptCore and SpiderMonkey use, at each operation's boundary and wherever it would otherwise translate a library failure.
### Deep-comparison work {#rdfc-work} When `rdfDeepIterations` is finite, a [=canonicalizing producer=] and an [=exact decoder=] MUST bound RDFC-1.0's deep comparisons [[RDF-CANON]] by `min(B × B, rdfDeepIterations)`, where `B` is the number of distinct blank nodes allocated in the complete internal dataset, primary and auxiliary alike. They MUST count `B` from the bounded dataset itself, and MUST NOT estimate it, count it per category or take it from the caller. Exhausting the allowance MUST fail with `RDFC_RESOURCE_LIMIT`. When `rdfDeepIterations` is `Infinity`, they MUST NOT bound the deep comparisons, and the `B × B` term does not apply. Neither exhaustion nor cancellation is authority to keep input IDs, switch algorithms, emit partial output or continue without graph canonicalization; this follows RDFC-1.0's requirement to defend against pathological datasets.
The reference implementation passes `maxDeepIterations` with this value, or `Infinity` when the allowance is unbounded, to `rdf-canonize`, rather than relying on the library's default, together with `algorithm: "RDFC-1.0"`, `messageDigestAlgorithm: "sha256"`, a `canonicalIdMap`, `rejectURDNA2015: true` and the operation's combined cancellation signal.
### Cancellation and deadlines {#cancellation} Canonicalization and decoding are asynchronous, so that graph canonicalization can be cancelled cooperatively. A [=canonicalizing producer=] and an [=exact decoder=] MUST accept a cancellation signal, and MUST fail with `ABORTED` when they observe cancellation and with `DEADLINE_EXCEEDED` when `deadlineMs` expires. Cancellation MUST be observable at every expensive stage, including the graph verification of decoding. Cancellation and resource outcomes depend on the caller's limits and on execution, not only on the input; [[[#validation-order]]] specifies when an observed cancellation ends processing. When `deadlineMs` is `Infinity` there is no deadline, and cancellation still applies. A finite deadline longer than the host's largest timer delay MUST expire at its actual time, never earlier.
The reference implementation accepts an `AbortSignal` and combines it with the deadline into one signal for each operation. It arms no timer for an unbounded deadline, and re-arms a timer whose remaining time exceeds the 231 − 1 ms that `setTimeout` can schedule. The reference application keeps A8's former defaults as its own browser policy, and checks requested deadlines, input sizes and depths against A8's former upper bounds. In a browser, the reference application runs canonicalization and graph-verifying decoding in a dedicated worker, not in an asynchronous function on the main thread, and transfers bytes rather than documents. A document cloned for rendering in another context is therefore not admitted for encoding there. Cancellation invalidates the request at once, sends cooperative cancellation, and terminates a worker that has not responded after a 250 ms grace period; the worker is also terminated when its deadline expires, whatever the graph library's polling frequency. Each result is bound to a request ID and a load generation, and stale results are discarded. None of this changes canonical bytes or adds to the operations this specification defines.
## OWL mapping {#owl-mapping} An [=OWL mapping adapter=] maps an OWL 2 ontology and its imports closure to a document of the [=structural-content profile=], under one of the mapping profiles of [[[#mapping-profiles]]]. The source bytes, their media type, the base IRI, import resolution and parser diagnostics belong to the adapter, not to the canonical core.
Consolidated from design section 21, the OWL-specific statements of design sections 10, 11.2, 11.5 and 13, and core contract A9, A9.1 and A9.2, with requirement keywords added; the mapping-profile identifiers are in [[[#mapping-profiles]]], and A9.3 is in [[[#migration]]]. The adapter bounds of the [unbounded-limits amendment](../specs/2026-10-27-canonical-vowl-unbounded-limits-amendment.md) are in [[[#mapping-limits]]]. A9.2's "corresponding mapping code" for a strict failure is read as the code of the compatibility recovery for the same condition, and its "exact source constructor kind" as the constructor name of the OWL 2 Structural Specification, which the reference implementation and the independent OWL mapping corpus both use. Release-specific parser support and the reference implementation's interface are in notes. Apart from this section's four clarifications recorded in [[[#accepted-clarifications]]], no rule was added or removed. The reference implementation's options, profiles, recoveries, exclusions and diagnostics match this section.
### Mapping operation {#mapping-operation} A mapping takes: - the exact source bytes; - the document IRI, an absolute IRI [[RFC3987]] that the parser uses as its base, and that never stands in for a missing ontology IRI; - the media type of the source syntax, given explicitly; - the mapping profile, which is compatibility mapping by default, and any other value than the two identifiers of [[[#mapping-profiles]]] fails with `OPTION_INVALID`; - an optional import resolver supplied by the caller ([[[#mapping-imports]]]); and - the cancellation signal and resource limits common to every operation ([[[#errors]]]). An [=OWL mapping adapter=]: 1. MUST take a snapshot of the source bytes before any asynchronous step; bytes that cannot be snapshotted safely fail with `INPUT_TYPE`; 1. MUST parse the source with a parser for its media type, and MUST fail with `MAPPING_MEDIA_TYPE_UNSUPPORTED` when it has no parser for that media type, rather than detect another syntax; 1. MUST require well-formed source syntax under both profiles, and MUST fail with `MAPPING_SYNTAX_INVALID` otherwise: compatibility mapping MUST NOT repair malformed XML, Turtle, JSON-LD, Functional-Style Syntax, Manchester Syntax or any other grammar; 1. MUST map the structural model [[OWL2-SYNTAX]] of the parsed root ontology and its resolved imports closure, and MUST NOT apply a reasoner; 1. MUST construct the same [=normalized source model=] from the same parsed ontology, whichever supported syntax expresses it; 1. MUST preserve full IRIs and the exact lexical forms of literals; 1. MUST produce its document by canonicalizing that model as every [=canonicalizing producer=] does, under the [=structural-content profile=] only, and MUST NOT reconstruct an artifact from an automatic layout; 1. MUST return the immutable record `{document, mappingProfile, diagnostics}`, where `mappingProfile` is the identifier it applied and `diagnostics` are as in [[[#mapping-diagnostics]]]; and 1. MUST fail as a whole when any step fails, returning neither a partial document nor partial diagnostics.
The reference implementation exposes this operation as `fromOwl(bytes, {documentIri, mediaType, mappingProfile, resolveImport, signal, limits})` from `vowl/owl`, and parses with owlapi-js. Which media types an adapter supports depends on its parser release, which qualifies and reports them; this specification does not fix the list. A separately specified preprocessing step would be needed to recover malformed source bytes.
### Imports {#mapping-imports} An [=OWL mapping adapter=] MUST NOT fetch any resource itself: only the caller's resolver acquires imported documents. The resolver receives the authored import IRI, the IRI of the importing document and the operation's cancellation signal, and either returns the imported document's bytes, document IRI and media type, or reports that it cannot resolve the import. The caller's resolver is expected to honor cancellation and the caller's acquisition policy. - The adapter MUST snapshot each returned byte array before parsing it, and MUST apply the same input rules and the same aggregate limits to it as to the root bytes, checking those limits before it admits the returned content. - Without a resolver, or when the resolver cannot resolve an import, the import is unresolved, and the mapping profile decides the outcome ([[[#mapping-strict]]], [[[#mapping-compatibility]]]). - Cancellation, an expired deadline or an exhausted resource while resolving an import MUST fail the operation as [[[#errors]]] specifies; none of them is an unresolved import. - A resolver response that is not a record of exactly the bytes, document IRI and media type MUST fail with `OPTION_INVALID` at `/resolveImport`, and a field that the root input would reject MUST fail with the code it would raise there: bytes that cannot be snapshotted with `INPUT_TYPE`, and an invalid document IRI or unsupported media type at `/resolveImport/documentIri` or `/resolveImport/mediaType`. Neither is an unresolved import. - The adapter MUST map the root ontology and the resolved closure as a set of ontologies, without depending on the order in which they were resolved, and MUST standardize anonymous individuals apart by source ontology, as OWL 2 requires [[OWL2-SYNTAX]]. Only the root ontology's IRIs, authored direct imports and own annotations enter the document ([[[#ontology]]]).
The reference implementation's resolver is `resolveImport(importIri, {importingDocumentIri, signal})`, which returns `{bytes, documentIri, mediaType}`, returns nothing, or throws. Its private builder receives the parsed root ontology and the resolved closure directly, rather than serializing and reparsing a merged ontology.
### Rules of both profiles {#mapping-shared} - Use of a term in a well-typed OWL constructor establishes its role even without a declaration; this is structural mapping, not a recovery. - Class and individual punning produces two roles over one subject in both profiles. - An [=OWL mapping adapter=] MUST fail on malformed lists, conflicting endpoint categories, unknown constructor kinds, invalid IRIs or language tags, cyclic expressions and any unresolved semantic ambiguity, under either profile; compatibility mapping is not a general recovery. Source structure that cannot be given one unambiguous retained interpretation MUST fail with `MAPPING_AMBIGUOUS`. - A well-formed source that breaks an OWL 2 rule from which neither profile recovers, such as a reserved IRI used as an entity, an invalid facet or facet value, a literal with an invalid language tag, or a constructor below its minimum arity, MUST fail with `MAPPING_SOURCE_INVALID`, whose `details.restriction` names the rule. - An unknown constructor kind, including one that the parser reports as unsupported, MUST fail with `MAPPING_UNSUPPORTED_CONSTRUCT` under both profiles. - Both profiles MUST exclude positive and negative object-property and data-property assertions, and same-individual and different-individuals axioms, from canonical content. The adapter MUST report each excluded axiom with `MAPPING_EXCLUDED_AXIOM`, naming in its `details` the axiom's constructor as [[OWL2-SYNTAX]] does: `ObjectPropertyAssertion`, `NegativeObjectPropertyAssertion`, `DataPropertyAssertion`, `NegativeDataPropertyAssertion`, `SameIndividual` or `DifferentIndividuals`. - Annotations on an excluded axiom MUST be excluded and diagnosed with it, and MUST NOT be reattached to the axiom's participants. - Both profiles retain the individual roles and direct class memberships of [[[#individuals]]]. - Multi-property data quantification MUST NOT be approximated by unary restrictions ([[[#expressions]]]): strict mapping fails with `MAPPING_UNSUPPORTED_CONSTRUCT`, and compatibility mapping omits the whole axiom with a `MAPPING_UNSUPPORTED_CONSTRUCT` diagnostic. - The adapter MUST NOT omit any other unknown construct silently. ### Strict mapping {#mapping-strict} A strict [=OWL mapping adapter=]: 1. MUST require a complete resolved closure, and MUST fail with `MAPPING_IMPORT_UNRESOLVED` when an import is unresolved; 1. MUST check the complete closure for OWL 2 DL structural conformance [[OWL2-SYNTAX]] before applying the version 1 retention boundary, including reserved vocabulary, category separation, the simplicity and regularity of properties, and the other global restrictions; 1. MUST NOT describe a partial check as strict: a capability that its OWL implementation lacks is implementation work, not permission; 1. MUST reject role combinations that OWL 2 DL forbids, violations of the global restrictions, unconsumed or ambiguous source structures, invalid lexical forms of literals, and unsupported constructs that would need approximation; 1. MUST fail with `MAPPING_DATATYPE_UNVERIFIED` for a literal whose datatype it cannot verify, rather than assert a lexical validity it did not establish; 1. MUST fail, for each condition that compatibility mapping recovers from, with that recovery's code ([[[#mapping-compatibility]]]); and 1. MUST diagnose the exclusions of [[[#mapping-shared]]] after the structural check, as intended exclusions rather than parse failures. ## Historical VOWL-JSON and migration {#migration} Canonical VOWL replaces the historical VOWL-JSON shape; it does not extend it. This section describes the one historical [=dialect=] that a [=migration adapter=] recognizes, and specifies how such an adapter converts it into a document of the [=structural-content profile=] or the [=artifact profile=]. Migration is one way: there is no Canonical VOWL to historical output, and no runtime fallback.
### The historical dialect WebVOWL historically stored and exported each visualization as one JSON object, commonly called VOWL-JSON. Each drawable record in `class`, `datatype` or `property` is paired with an attribute record in `classAttribute`, `datatypeAttribute` or `propertyAttribute`, joined by an operation-local `id`. Beside these parallel arrays sit `header`, `namespace`, `metrics`, `settings` and an informative `_comment`. No specification defines that shape. The VOWL 2 specification [[VOWL2]] defines a visual notation only, and the VOWL article [[VOWL-ARTICLE]] names VOWL-JSON as the format WebVOWL uses without specifying it. Its meaning came from the producing implementations. This specification recognizes exactly one dialect: the JSON written by this repository's export path at commit `354ed3af8c1e82019f6280b2594acaceac96cca0` [[WEBVOWL-354ED3AF]]. That export cloned its stored model, sorted selected arrays and object keys, and copied every other stored field unchanged, while WebVOWL's loader accepted broadly shaped objects. Neither the exporter's `_comment` nor its revision therefore establishes a closed grammar; [[[#migration-grammar]]] supplies one. The dialect does not preserve several distinctions that Canonical VOWL retains: - full annotation predicate IRIs: the exporter percent-decodes local names, so `%61` and `a` produce the same identifier; - the datatype of literals written without a language tag; - whether a property's domain and range were asserted, defaulted, or derived from an inverse property; - the complete operands of class operators, and the scope, filler and exact bounds of restrictions; - whether equivalence or disjointness among three or more classes came from one axiom or from several pairwise axioms; - the identities of the members counted by `instances`; - annotations nested more than one level deep; - viewport dimensions and the effective hidden set, because only zoom, translation and filter controls are saved; and - the predicates behind the header summaries `title`, `description`, `author` and `version`, which could also be edited independently of the annotations they summarize. Migration therefore recovers only facts that the input represents unambiguously, and fails where a required distinction was lost. It never invents an annotation IRI, an ontology identity, a viewport or a semantic category.
The evidence behind each disposition in this section, with line references into the source at the pinned commit, is recorded in the [dialect inventory](../reviews/canonical-vowl-legacy-dialect-inventory.md) and the [legacy ingress contract](../reviews/canonical-vowl-legacy-ingress-contract.md).
### Dialect identifier {#migration-dialect} The only dialect identifier this specification defines is: ```text webvowl-legacy-354ed3af8c1e82019f6280b2594acaceac96cca0 ``` References to source files in this section mean their content at that commit [[WEBVOWL-354ED3AF]]. A [=migration adapter=] MUST require the dialect identifier explicitly, and MUST NOT infer a dialect from the shape of the input. An unrecognized identifier MUST fail with `MIGRATION_DIALECT_UNKNOWN`. Recognizing any other historical dialect requires its own named contract and conformance fixtures; this specification defines none. ### Migration operation {#migration-operation} A migration takes: - the exact input bytes; - the dialect identifier; - the target profile, which MUST be the [=structural-content profile=] or the [=artifact profile=]: there is no default, and any other value fails with `OPTION_INVALID`; - a set of caller [=resolutions=], empty by default; and - the cancellation signal and resource limits common to every operation ([[[#errors]]]). A [=migration adapter=]: 1. MUST take a snapshot of the input bytes before any asynchronous step, decode them as UTF-8 [[RFC3629]] without replacement, and validate them as JSON [[RFC8259]] with duplicate member names detected before any object is constructed, as an [=exact decoder=] does ([[[#encoding]]]); 1. MUST admit only input that satisfies [[[#migration-grammar]]], and MUST apply the dispositions of [[[#migration-grammar]]], [[[#migration-annotations]]] and, for the artifact profile, [[[#migration-artifact]]]; 1. MUST produce its document by canonicalizing the recovered source model as every [=canonicalizing producer=] does, so that the result is an admitted [=Canonical VOWL document=] of the target profile; 1. MUST return the immutable record `{document, dialect, diagnostics}`, where `dialect` is the identifier it applied and `diagnostics` are as in [[[#migration-diagnostics]]]; 1. MUST fail as a whole when any step fails, returning neither a partial document nor partial diagnostics; and 1. MUST NOT fetch any resource, select a dialect automatically, render, or run a layout algorithm. Legacy `id` values serve only to join records and to establish correspondence within one operation; they MUST NOT appear in the result.
The reference implementation exposes this operation as `migrate(bytes, {dialect, profile, resolutions, signal, limits})` from `vowl/migrate`.
### Diagnostics {#migration-diagnostics} A migration [=diagnostic=] is the closed record `{code, severity, sourcePointer, details}`. `code` is `MIGRATION_DROPPED_FIELD` or `MIGRATION_RESOLVED_FIELD`; `severity` is `"warning"`; `sourcePointer` is a JSON Pointer [[RFC6901]] into the original input, including its `~0` and `~1` escapes; and `details` is bounded explanatory text outside canonical identity, which never replaces the stable code. - Every discarded field that is not canonical content MUST receive a `MIGRATION_DROPPED_FIELD` diagnostic. A diagnostic on a container MAY cover its whole subtree when all of it is discarded; when some children are retained, each discarded child MUST be diagnosed instead. - Each consumed resolution MUST produce a `MIGRATION_RESOLVED_FIELD` diagnostic at its `sourcePointer`. - Identical diagnostics MUST be deduplicated, and diagnostics MUST be ordered by the unsigned byte order of the UTF-8 RFC 8785 serialization of each complete record, as mapping diagnostics are ([[[#mapping-diagnostics]]]). - Diagnostics MUST NOT enter canonical bytes. ### Errors {#migration-errors} | Code | Raised when | | --- | --- | | `MIGRATION_DIALECT_UNKNOWN` | The dialect identifier is not one this specification defines. | | `MIGRATION_AMBIGUOUS` | The input contains an unknown field, an unsupported shape, conflicting parallel fields, a dangling reference, or a distinction that cannot be recovered; or its artifact state cannot be matched unambiguously to the canonical occurrences. | | `MIGRATION_RESOLUTION_INVALID` | A resolution is malformed, duplicated, unused, conflicting, of the wrong kind for its location, or supplied for a location that is already resolved. | A `MIGRATION_AMBIGUOUS` failure MUST identify the source pointer at which it occurred. A [=migration adapter=] MUST resolve the named identities of the pairs and then reject any pair graph that contains a complete triangle, because one n-ary axiom over three or more classes and the corresponding pairwise axioms produce the same pairs. A triangle-free pair graph retains each represented pair as a separate binary assertion; a chain of three classes is not by itself ambiguous. Triangles MUST be detected on the resolved named identities, not by counting traversal IDs. Projection may later group a connected component into one occurrence ([[[#projection]]]); the assertion records remain distinct.
This rule follows an observed collision, not a preference. Through the pinned producer, `EquivalentClasses(A B C)` and its three pairwise axioms produced identical 1,771-byte outputs, and the analogous disjointness inputs identical 2,027-byte outputs.

#### Occurrence correspondence and placements {#artifact-placements} - Each admitted named class or equivalence group corresponds to the canonical occurrence over the same retained target roles, and each admitted subclass or disjoint relation corresponds to its canonical edge. Subclass edges also have positionable labels. - A legacy property record's `pos` is a label position, never an edge placement. A canonical disjoint edge has no positionable label, so its legacy `pos` and `pinned` drop with diagnostics and create no placement. - Every canonical positionable [=occurrence=], including hidden ones, MUST receive a recoverable finite position and an explicit Boolean pin. - When several source records contribute to one canonical occurrence, every position and pin they supply MUST agree. One saved representative MAY establish a group's placement when the other records make no placement claim; a conflicting claim is fatal, and the adapter MUST NOT pick the first record. - Unmatched saved placements and missing placements for new occurrences are fatal. Generated historical operator links and changed generic splits never justify synthesizing coordinates. - The correspondence is local to the operation, and is not stored as durable legacy IDs.
The historical runtime saved one representative class-node target and gave both targets of an inverse property the same label position, and its arrangement writer skipped matches that were not unique. A missing placement on a hidden or newly split occurrence is therefore a genuine migration error, while an equivalent alias without its own coordinates does not by itself make a placed group unrecoverable.
#### Camera {#artifact-camera} A [=migration adapter=] MUST consume the `viewport` resolution at `/settings/global/translation`, and compute the camera centre from the saved translation `(tx, ty)`, zoom `z`, and the resolved width `w` and height `h`: ```text center.x = (w / 2 - tx) / z center.y = (h / 2 - ty) / z ``` Without that resolution, artifact migration fails with `MIGRATION_AMBIGUOUS` at that pointer. Nonfinite results MUST be rejected. The positive zoom is retained as the camera's `zoom`, the viewport dimensions are discarded after conversion, and the translation is never interpreted as the centre. The [historical transform](https://github.com/Hadden-Industries/webvowl/blob/354ed3af8c1e82019f6280b2594acaceac96cca0/src/webvowl/js/runtime/renderedGraphInternals.js) applied translation and then scale; [[[#artifact-grammar]]] fixes the canonical formula.

### Conformance corpus {#corpus} The conformance corpus is in [`packages/vowl/conformance/`](../../packages/vowl/conformance/README.md), together with the notes that reproduce it. - A vector records its source or input bytes, its profile and operation, and either its expected document and exact canonical UTF-8 bytes or its stable error. - A mapping vector also records the expected internal dataset, its canonical N-Quads and the correspondence of primary nodes to categories, so that ID issuance can be checked independently. - For a symmetric source, a fixed-input identifier map records one labelling; permutations are compared by their complete output, never by a supposed durable correspondence of source handles. - Canonical documents and canonical N-Quads are compared as exact bytes, and mapped datasets by RDF dataset isomorphism; private blank-node labels and line order are not part of the contract. - The manifests pin each file by SHA-256 and byte length, and they and any output digests are conformance artifacts, never fields of a document. ## Security considerations
Consolidated from design section 22, on the separation of canonical bytes from digests and signatures; the rest of this section summarizes requirements stated elsewhere, and adds none.
Every input to a [=canonicalizing producer=], [=exact decoder=] or adapter can be hostile. - **Exact decoding without repair.** A decoder accepts only canonical bytes, and fails rather than repairing, coercing or ignoring anything ([[[#exact-decoding]]]). Duplicate member names fail before either binding can be lost ([[[#duplicate-members]]]), so one document cannot show different content to parsers that keep different bindings. - **Failing closed.** Every operation either succeeds completely or fails with one bounded error ([[[#failing-closed]]]), whose details copy no unbounded input and no stack trace ([[[#error-object]]]). Only a document that the same implementation instance admitted can be encoded ([[[#canonical-encoding]]]), and in-memory input is snapshotted before the operation first suspends, so that later changes to it cannot affect the result ([[[#in-memory-input]]]). - **Resource exhaustion.** Limits bound the work of every operation ([[[#limits]]]). Most have no default and are the caller's to set: a caller that processes untrusted input should set them. The defaults that remain bound nesting, RDFC-1.0's deep comparisons, elapsed time and XML entity expansion, for the reasons the note in [[[#limits]]] gives. Exhausting the deep-comparison allowance on a poison dataset never permits a fallback ([[[#rdfc-work]]]). A lifted limit hands the bound to the host runtime, whose memory exhaustion can end the worker or process without a reportable error ([[[#host-limits]]]). - **No network access in the core.** Validation never dereferences a profile identifier or acquires a schema ([[[#profile-resolution]]]), and canonicalization never dereferences the mapping vocabulary ([[[#rdf-vocabulary]]]). An [=OWL mapping adapter=] fetches nothing itself: only the caller's resolver acquires imports, under the caller's acquisition policy, and each response is snapshotted and bounded like the root input ([[[#mapping-imports]]]). - **Digests and signatures.** Canonical VOWL defines bytes, not a digest or signature scheme. A consuming security protocol selects its digest or signature algorithm; the profile identifier inside the bytes separates the format from others, while algorithm identifiers, keys, proofs, timestamps and verification policy belong in that protocol's envelope. Equal bytes identify the same normalized VOWL model, not the same source bytes, imports or axiom set ([[[#introduction]]]), so a signature over a document attests to that model only. - **Retained claims.** The qualifications of the [=compatible-artifact profile=] are claims of the operation that captured them; reopening a document grants no authenticity to an original source ([[[#compatible-grammar]]]).
The reference implementation does not claim to sandbox a hostile JavaScript `Proxy` ([[[#canonicalization-algorithm]]]).
## Privacy considerations
This section summarizes requirements stated elsewhere, and adds none.
- A structural-content document records the retained VOWL structure of an ontology, including its IRIs, labels and annotation values, and so reveals what the ontology describes. - An artifact document also records portable visualization state: positions and pins, the camera, the hidden set, label selection, display prefixes and display modes ([[[#static-snapshot]]]). This state can reveal how a person arranged and curated a view. It excludes session state, such as forces and timers, viewport and device details, themes, hover, focus, selection, search, editor mode and open panels, so a document carries none of them. - Migration keeps only the portable state of a historical artifact, and drops its force-layout parameters, interaction and styling choices and paused state ([[[#migration-artifact]]]). - A compatible-artifact document also retains the IRIs of its source documents and imports, the decisions and assessments that qualify its interpretation, and the source statements that the view did not interpret, which can include content that the visualization does not show ([[[#compatible-artifact]]]). Original source bytes, acquisition locations and digests stay outside it. - Source bytes, document locations, redirects, cache locations, acquisition provenance, parser messages and [=diagnostics=] are never part of canonical bytes ([[[#non-goals]]], [[[#mapping-diagnostics]]]). A caller that shares diagnostics shares that information separately from the document. - An error's details are bounded and copy no unbounded input value ([[[#error-object]]]).
## Internationalization considerations
This section summarizes requirements stated elsewhere, and adds none.
- Every string is [=Unicode-valid=] ([[[#unicode-admission]]]). Apart from lone surrogates and the noncharacters that I-JSON prohibits, every character is retained, and no Unicode normalization is applied, so strings that differ only in normalization remain different ([[[#canonicalization-algorithm]]]). - IRIs keep their exact spelling, internationalized IRIs included: no case folding, percent-decoding or Unicode normalization ([[[#notation]]]). - Language tags of structural literals are checked for well-formedness, and lowercased by ASCII rules without any other normalization ([[[#literals]]]). The residual literals of the [=compatible-artifact profile=] keep their language strings exactly as reported, and a reported base direction as data ([[[#residual-statements]]]); directional language strings are otherwise outside version 1. - Label selection never depends on a locale. A language range selects labels by RFC 4647 lookup [[RFC4647]], candidates of equal precedence are ordered by UTF-8 bytes rather than collation, and English is not an implicit fallback ([[[#label-selection]]]). No ordering in this specification uses locale collation ([[[#collections]]]). - The whitespace of the IRI-derived fallback is a fixed list of code points, not a runtime's Unicode tables ([[[#iri-fallback]]]), and the fixed phrases and built-in names that label selection uses are English ([[[#fixed-label-wording]]]).
