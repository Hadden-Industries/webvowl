WebVOWL ontology loading: Chromium performance consultation
30 October 2026

Question

How can the current, validated ontology-materialization path reach the
user-visible performance of original WebVOWL 1.1.7? Chromium is the first
priority. We want trace-supported implementation changes with unchanged
validation, source preservation, ownership and recovery guarantees.

Measured comparison

Three paired local runs used Chromium 156.0.8078.4, Playwright headless-shell
build 1248, a 1440 x 1000 viewport, identical seven hash-pinned source
documents and logical IRIs, and production-mode frontend assets.

frames, in milliseconds:

Architecture and comparison boundaries

Original: actual WebVOWL 1.1.7 WAR and unmodified OWL2VOWL 0.3.7 HTTP
conversion service. A fresh JVM is ready before each cold browser request;
warm runs retain that JVM. The retained archive is hash-checked by the
harness. Existing Java 25/Tomcat 8.5.16 compatibility settings are used;
this does not reproduce the historical Java 8 deployment.

Current: browser attempts direct source acquisition, encounters genuine
CORS denial, and uses the local HTTPS materialization provider. The provider
validates and publishes each document. Browser consumption verifies the
immutable evidence chain and exact artifact bytes. A dedicated worker then
loads the import closure through public OwlAPI APIs, assesses it, constructs
and admits the retained VOWL model, and creates its recovery checkpoint.
The application owns drawing and inspection copies. Node is 26.13.0 on
Windows x64; the provider's bounded parser-initialization reuse is enabled.

Cold has a fresh browser, empty provider and seven origin acquisitions.
Both warm paths have zero origin and control-plane calls and 36 static cache
requests. Same-page warm may reuse a private completed result only after
fresh source/context checks. Fresh-browser warm creates a new worker and
performs full browser-side processing. That distinction is essential.

The corpus is UO extended, core, reference data, ISO/IEC 11179-3, Gregorian
time, OWL-Time and SKOS. Both paths retain all checked legacy named entities
(806 class/datatype IRIs and 763 object/data-property IRIs), and all seven
documents resolve. This is coverage evidence, not full axiom equivalence.

Representative current fresh-browser sample (3996.2 ms total)

Worker loading:              1047.9 ms, including about 50 ms import waits
Source/profile assessment:    283.0 ms
Model projection:             723.5 ms, including 583.9 ms normalization
Evidence retention:             7.4 ms

These spans are not a complete critical-path or exclusive CPU profile.
Worker bootstrap, transport, copying, scheduling and GC need attribution.
WebKit-specific timings and isolated microbenchmarks are not Chromium proof.

Work already completed

The public OwlAPI 0.1.0-rc.3 artifact is pinned in provider and consumer.
Qualified source: 17cdb60b3a2920b7cb4da0000e87b374dedb578a.
Completed changes include adaptive bounded polling, one-sibling byte
prefetch with ordered native parsing, independent metadata-read overlap,
shared-policy cancellation repair, bounded provider parser reuse, exact IRI
lexical-proof reuse, private validated warm results, and equality-subtree
serialization reuse. The component checks and three-engine integration pass.
The performance gate still fails cold and fresh-browser warm.

Long-ASCII scanning and pointer-free tree walking produced no useful
measured gain and were removed. A metadata-hash overlap experiment had only
a small gain and exposed an intermittent cancellation-test timing failure;
it was removed with the original failure retained. No tests were weakened.

Questions for the expert

1. Capture Chromium CPU/allocation and timeline traces for the original and
   current cold and fresh-warm cases, including the dedicated worker. Which
   functions and waits actually dominate? Stage timers alone are insufficient.
2. What explains the cold-only excess beyond fresh-browser warm: provider
   initialization, validation, admission/status polling or serialized imports?
3. Can private structural ownership be constructed once during fresh OWL
   admission? openOwlState snapshots and relabels a private structural tree;
   admit snapshots it again. Full validateStructure and publication checks
   must still run, with exact resource accounting and caller isolation.
4. Are runtime schema compilation, repeated normalization graph construction,
   structured clones or GC material? Graph passes straddle mutations, so reuse
   needs explicit validity conditions. Schema precompilation is unmeasured.
5. Rank a small number of fixes by expected critical-path saving, evidence,
   correctness risk and verification cost. Identify any unavoidable architecture
   cost and the concrete trade-off needed to remove it.

Required invariants

Preserve exact decoded bytes, logical/parser contexts, complete imports,
digest/evidence checks, full source/profile and model validation, qualified
heuristic mapping, private model ownership, checkpoint recovery, cancellation,
heap/work deadlines and finite acquisition bounds. Keep the accepted painted
generation and original rendering defaults as the measurement boundary.
Maintain production cache activation disabled. No push, deployment, paid
module, package change or new public service contract is authorized here.
